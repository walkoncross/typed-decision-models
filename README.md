# typed-decision-models

搜集 **jev 类模型 / 类型化决策模型(typed decision model)** 的实现方法。

这类模型的共同点是:不把 LLM 当生成器用,而是把同一份权重当**分类器**读——一次前向、只取读位置的 logits、掩码到固定标签集、重归一化。于是输出被封闭在一个已知标签集上,没有文本需要解析,也没有东西可以幻觉。代表场景是 JevBench 式的"给定一段 state,在若干选项中选一个"。

前四篇正文均未改动,只在文首补了代码库地址与「行号相对仓库根目录」的说明,并把指向 RYOTIDE 那篇的路径改写为本仓库内的相对路径。Laya、SemIf-OpenJev、OpenJev(HF)、Semantic Router、CLM、Kev、decider、Nimble、Jevlike 与 H2O-Lightning 十篇同理在文首带代码库地址与行号基准说明,但它们没有上游原件可比对——改它们就是在改唯一的一份。这十篇「非副本」里,只有 OpenJev(HF) 与 H2O-Lightning 的上游不是 Git 代码仓,`git clone` 得到的是权重仓(LFS 需跳过);Semantic Router 的上游是 Git 仓,但它是十四篇里体量最大的一个:一个 Go 控制面 + 一个 Python 运行时 + 一套 JevBench 闭环评测,本文只走「类型化决策」这一条线。CLM 的上游同样没有走查稿(`docs/` 下只有一份给 agent 的自动调参说明),但它与另外十三篇有一处不同:**它把跑分记录连同结果一起提交进了仓库**(`examples/t_rex/results/*.json`),所以那篇的实例走查是在 committed 产物上重算,而不是引上游文档里的数字。Kev 与它相邻:上游**没有**提交评测记录的那份完整转储,但提交了 `rows.json` / `report.json` 这类**读数摘要**与一份发布清单(`runs/release/kev-1.0-manifest.json` + `SHA256SUMS.txt`),所以 Kev 那篇的「实测」是在这些 committed 产物上重算公式、并对发布清单做 sha256 对照。Nimble 与这两条同属「有 committed 产物可重算」的一类,但可重算的东西不同:它的 `examples/*.json` 与 `docs/assets/*.json` 里既有**读数链本身的记录**(`logits` / `scores` / `probabilities` / `confidence` / `usage`),也有**13 个公开子集的 manifest**(ids、计数、校验和),所以那篇的「实测」有三类——读数公式的复算、托管面 `confidence` 与 `score` 的逐位吻合、以及 manifest 内计数的加总;代价是它**没有**一份像 Kev 那样的「发布清单 vs 模型卡」对照物。Jevlike 是这条光谱的另一端:**它提交了三个检查点,却没有提交任何评测记录**——`runs/` 与 `data/` 都在 `.gitignore` 里,`examples/*/README.md` 里的每个数字(kills、胜负和、逐键准确率)都没有对应的 jsonl 随仓提交,所以那篇的「实测」只能落在**权重与容器**这一层:检查点的 zip 条目长度算术、pickle 键名字符串给出的训练谱系、以及三个检查点选项表的逐行算术。H2O-Lightning 与这两条又不同:它提交的不是读数记录也不是权重,而是一整套**升级阈值分析**——`routing_reproducibility/` 里有两份第三方题集(2,000 + 1,474)、3,474 行逐题读数、一个纯标准库重算脚本和一份覆盖 7 个文件的 `SHA256SUMS`,所以那篇的「实测」有四类:哈希清单全过、内部计数(行数 / 题型分布 / 温度字段)互证、**用走查自己的代码把发布的阈值表重算一遍并与卡片逐格比对**、以及复现上游自陈的三个量(两次 pass 差额的逐题最大差中位数 0.000500、9/3,474 个 top 答案不同、地板使 t=0.8 的 noul 升级率从 41.0 % 变 0.0 %);代价是它**没有**一份「发布清单 vs 模型卡」的 sha256 对照物,权重本身(9.1 GB)也没核。

十四条路线可以放在一起读,分歧集中在「读位置怎么定、置信度从哪来」:

- **RYOTIDE**:零训练,把冻结 LLM 读成分类器——运行期标定读位置、掩码 + 重归一化,`marker_mass` 是它的诊断量;
- **Jeff**:在 RYOTIDE 那条读法之上**训一个决策头**,`slice_init_` 让训练起点逐位等于零样本读法;
- **Open-Jev**:把决策拆成 N 个 pointwise 的是非题,再训一个 `Yes − No` 播种的标量头读成校准打分;
- **Quyet**:自训权重,encoder 用 `[MASK]` 槽位、LLM 用字母 `A..J`,温度随权重一起发布;
- **Laya**:双向编码器,把决策改造成**填空题**——每个选项一个 `[MASK]` 槽位,一次前向读 K 个标量;顺序偏置在训练时用 `parallel` 布局消解,另有一个不跑模型的**路由器**逐请求挑 checkpoint;
- **SemIf-OpenJev**:同样零训练,但把读法工程化到**三个运行时 + 一个浏览器**,并配一条独立的校准链——读末位的字母槽位 `A`–`P`,顺序偏置不消除只度量(反转选项顺序翻转 10/36 的 argmax),浏览器那条路径是「**会生成 1 个 token**」这一侧的第一个例子;
- **OpenJev(HF)**:微调过的 27B + 一个挡在 vLLM 前面的 HTTP 补丁——读**第一个输出位置**上 52 个字母的 logits,训练把顺序偏置从 18.5% 压到 2.3%,而 T=0.85 / noul 的 (1.829074, 0) 是训练之后施加的常数,且**代码里的默认值与发布配方全都不同**;
- **vLLM Semantic Router**:不是一篇读法而是一个**运行时**——同一个 `/v1/decisions` 底下挂三代模型、三套读出协议(encoder 的 `[MASK]` 槽位 / decoder 的选项端点 / Vela 2.0 的八个标记 token)与四档数值 profile,`exact` 的目标是与发布包**逐字节相同**;Go 控制面拿到 typed answer 后**不用**模型报的 `confidence`,而是自己从 `probabilities` 重算一个,并拿 JevBench 标定自己的升级门;
- **CLM**:把决策整个换掉——不读 logits、没有词表,一次决策是**状态嵌入与候选嵌入的一次点积**;于是候选可以长期缓存、状态才需要现算,`marker_mass` 这类诊断量在这里没有对象,而**读位置被推给了编码器服务的池化默认值**(本仓不设定、不断言、不记录),整条链上也没有任何标定,`temperature` 只是每请求的入参且不回声。
- **Kev**:换掉的是「标签集从哪来」——**用户声明的每个选项就是一段 `<opt>…</opt>` 跨度**,骨干加载时直接丢掉 vocab head(`model.py:257`),所以既没有词表可以掩码、也没有「重归一化」这一步,softmax 落在头给出的恰好 K 个标量上;它付的代价是**必须训一个头**(`PointerHead` 的 q/k),换来的是候选集不受分词器约束、**读位置由 `encode` 在构造序列时算出来**因而运行期没有可标定的自由度;顺序偏置在训练期每 epoch 打散(外加一个构造性不变的开关 `option_isolation`,默认关且混合骨干不支持),运行期只度量、而**发布卡片不给翻转率**。
- **decider**:读法与 RYOTIDE 同源(标签行 logits → 掩码 → softmax),但**一次前向读 K 个槽位**——每题一个 `Answer k: (` 的左括号,全部落在同一行里,所以多问一题不改变任何已有答案;「typed」来自分词器里 **255 个单 token 标签**,而**同一个读法读两种权重**:自训的 0.8B–35B,以及不改权重、只靠一个 `decider_config.json` 的 chat 布局读进来的 stock 指令模型(后者在 Decision Index 上把自家训练的三个尺寸都压过);它把 RYOTIDE 的 `marker_mass` 变成了**概念不适用**——读出头就是 `lm_head` 的 255 个标签行,词表维度从不出现,标签外的质量在数学上不存在;置信度上有一处同名不同公式:`system_one()` 报 TypeSafe 的 rescale,`decide()` 报 `p_max`。
- **Nimble**:读法同样与 RYOTIDE 同源,但**一次前向只投影候选的那 K 行**(`full_vocabulary_projection: False`),所以「掩码 + 重归一化」在主路径上不存在;「typed」来自**按位置分配**的 26 个单 token 字母码(255 走另一套扩展编码器,且**已发布的托管端点只开到 26**);它把 RYOTIDE 的运行期标定换成了**训练期钉死**,代价是 **prompt 源码的 sha256 成了权重的一部分**——`schema_config.json` 里的 `prompt_code_sha256` 在加载、LoRA 合并、起服务三处各重算一次,不符即拒;它是十四条里**唯一一份代码同时给出三个服务面**的路线:本地 MLX/CUDA 两个 scorer 不生成任何 token,legacy `QwenEnumScorer` 走一次 1-token 解码,托管面则每 field 一个 token 外加一个丢弃的 warmup(3 题对应 `usage.output_tokens: 4`);顺序偏置**训练期打散、运行期连一次对照都没跑过**(工具在,`docs/PUBLIC_BENCHMARKS.md` 明说未测)。
- **Jevlike**:换掉的不是读法而是**两件更靠前的事**。①**链上没有 LLM**:默认骨干是从头训的字节嵌入(`nn.Embedding(257)`,`model.py:49`),可选路径是冻结编码器 + 掩码均值池化;②**标签集就是这一行的选项列表**——`label` 是行内下标(`data.py:30-31`),`cross_entropy` 直接落在这行的 N 个标量上,于是「标签必须单 token」「字母表上限」「候选数上限」三类约束同时**没有对象**;读法上它是**每个选项自己对 state 做一次注意力加权平均**(`model.py:34-42`),一次前向里两个 softmax(内层在 state 位置上、外层在选项上),所以「读位置」这个变量不存在,取而代之的是一张**逐选项的权重分布**——视觉侧把它量出来(归一化熵、peak、与敌人位置的相关、真实/空白/平均/打乱 patch 四组 KL,`audit.py:137-176`),**文本侧一个都没有**;置信度上它是继 CLM 之后第二条**零标定**路线,而且更彻底——全仓唯一的 `temperature` 是下棋时采样按键的旋钮(`examples/chess/eval.py:72-73`),连"每请求入参"这一层都没有;另外它是唯一一条**同一个头既读文本又读画面**的(8×10 个 patch、12 行共享控制器表、Doom 0–6 与象棋 7–11)。
- **H2O-Lightning**:读法与 RYOTIDE 同源,但它把「typed」从**构造**改成了**证明**——`serve_config.json` 里那 255 个标签里有 178 个是 BPE 片段(`in`、`the`、`ing`…),凭分词器根本保证不了单 token,所以 shim 在**首次请求**时用真实 prompt 逐个探针,要求 `tokenize(text + " " + 标签)` 恰好比 `tokenize(text)` 多一个 token 且 id 互异,不符即 503 拒服务(`h2o_lightning_shim.py:936-944`);读位置也不是标定出来的,而是 prompt 末尾那句字面量 `Answer:` 之后的那个位置(`:167-168`),运行期没有扫描、没有候选位置、没有阈值——标定被换成了**训练期钉死 + 加载期证明**。读数上它**只把候选的 K 个 token id 当请求参数发给 vLLM**(`logprob_token_ids`,:842-845),所以词表维度从不出现、`marker_mass` 概念不适用(与 decider / Nimble / Kev 同一个结论、第四种机制),代价是 255 个标签要分两次 completion(vLLM 单请求上限 128)。置信度是**读出来的**,但发布值被两个旋钮先后改写:逐题型温度(`choice 0.75 / noul 0.8 / score 0.65`,`serve_config.json:5`)与 yes/no 地板 `0.801`(`:6`,只抬不动 argmax,本文在 1,367 行上复算翻转 0 次),而这两个旋钮的来源会由 `/health` 如实回报(`noul_floor.source` / `temperature_source`,:1077-1078)——**改了数值的东西自己会说谁改的**。多问题共享 state 靠 vLLM 前缀缓存,shim 只把 `input_tokens` 的账单改对(共享头只计一次,:995-1001、:1059-1060);顺序偏置则是第三种状态:既不像 Kev 那样训练期打散、也不像 SemIf-OpenJev 那样反转一遍度量,**工具与度量都不在**(全仓对 `permut` / `shuffle` / `reorder` 零命中,部署者也没有可以自己跑一次对照的入口)。同一份代码里还有第二条服务面:带图的请求走 chat completions(assistant 轮用 `continue_final_message` 预填同一个 `Answer:`),外加一个**自带 SSRF 边界**的图像 URL 抓取器(只许公网 https、连到检查过的那个 IP、硬截止时间、先计数后抓取)。

共同底线只有一条,也是 RYOTIDE 第 13 节那四条不变量的来源:**一次前向、只读最后一个位置、掩码到已知标签集、重归一化,`output_tokens = 0`**。违反时数字会看似合理却是错的——十四条路线都在同一个主题上记录了各自的踩坑方式。两处例外都在「会生成 1 个 token」这一侧:SemIf-OpenJev 的浏览器路径用一次 1-token 的解码换一个能返回 logprobs 的接口,读的仍是被迫输出的那个 token 的 `top_logprobs`(其 §9);OpenJev(HF) 对 vLLM 发 `max_tokens: 1`,而响应里 `output_tokens: 0` 是**硬编码**的(其 §4)。Semantic Router 是这条底线上**最干净**的一条:`output_tokens` 在响应组装处硬编码为 0(其 §2.2),三套读法没有一条会生成 token。CLM 是另一头的极端:它连「一次前向」都不必改写——决策本身没有前向,`output_tokens: 0` 是字面量(其 §4),四个词里只剩「输出封闭在已知选项集上」还需要讲,而它靠的是**根本没有词表可越界**(其 §2.2)。Kev 是**字段层面唯一不成立**的一条:它确实不生成 token,但 `usage.output_tokens` 被定义成「序列化后答案 JSON 的 token 数」(`api.py:163-165`,README 第 284 行明说 *counts tokens in the serialized answers, not generated tokens*)——机制层面成立,字段层面不成立(其 §9.4);同时它也是第一条**连「掩码 + 重归一化」都不存在**的路线,所以那四个词在它身上只剩「一次前向」与「输出封闭在选项集上」。decider 与 Semantic Router 同类——`output_tokens: 0` 在它的三个服务与库入口都是响应组装处的字面量(其 §4.4、§9),而它唯一的例外也在「1 个 token」这一侧:`serve_vllm` 向 vLLM 发 `max_tokens=1, temperature=0.0, logprob_token_ids`,只为拿回那个位置的 logprobs,**不消费**采样结果(其 §4.4)。Nimble 是十四条里**同一份代码库内部就自相矛盾**的一条:本地两个 scorer 连「生成」这个概念都没有(统计里不存在 output token 这个字段),legacy `QwenEnumScorer` 走 `max_new_tokens=1` 的真解码(`enum_scorer.py:119`),而托管面是 SGLang 上**每 field 一个 token 外加一个丢弃的 warmup**——committed 的两次托管 smoke 记录里,3 个 field 的 `usage.output_tokens` 都是 **4**(其 §1、§13.3),上游文档也照写 *This is not a zero-generation backend*。所以引用 Nimble 的 `output_tokens` 之前,**先确认问的是哪个服务面**——这不是口径不同,是三个不同的入口。Jevlike 又是另一头的极端:它**没有服务、没有 `usage` 字段、也没有 token 计数这回事**(其 §8),四个词里只剩「一次前向」与「输出封闭在选项集上」还字面成立——**「掩码到已知标签集」与「重归一化」在这条链上都没有对象**(头只输出 K 个标量),而「只读最后一个位置」要改写成「每个选项自己对全部未掩位置做一次加权平均」(其 §4、§10)。H2O-Lightning 是这条底线上**最干净**的一条:`output_tokens: 0` 在响应组装处是字面量(`h2o_lightning_shim.py:1067`),图像路径也走同一个 `respond()`,所以两条服务面都是 0(其 §13);但另外三个词要改写——「只读最后一个位置」得说成「读渲染后 prompt 的下一位,而那个位置由末尾的字面量 `Answer:` 定义」,「掩码到已知标签集」则没有对象(候选 token id 是请求参数,词表维度从不出现,其 §5、§13)。

并读才看得见的东西(`enable_thinking=False` 的诸种接法、填充方向、混合架构的 cache 分支复制、温度口径、ECE 分箱不一致、已校准与未校准是两份文件、**代码默认值 ≠ 发布配方**、**同一个字段名在不同代际是两个公式**、**同一个字段名在两层是两个量**、**同一个包里两个 `confidence`**、**同一份代码库里两个服务面对 `output_tokens` 给出相反自陈**、**读位置被钉进权重的哈希**、**打散顺序的工具在、对照实验不在**、**「typed」可以从固定标签集改成实例自己的选项列表**、**不读位置的读法要换一套守卫(量注意力分布,而不是量位置对不对)**、**默认截断是静默的**、**「单 token」可以是运行期证明出来的性质而不是构造**、**改了发布数值的旋钮自己在 `/health` 里报告来源**、**同一份 README 里温度既是三个值又是一个值**)汇总在 [`docs/comparison.md`](docs/comparison.md)。

## 收录约定

新增实现或案例时,在 `docs/<实现名>/` 下建目录,一事一文,并在上表登记一行。同一实现的文档放在同一子目录里,文件名直接写主题(如 `typed-decision-model.md`、`calibration.md`),不再重复实现名。

跨实现的总表放 `docs/` 顶层(如 `docs/comparison.md`),不进任何单个实现的子目录——它不属于某一个实现,且这样各篇更新时顶层只需改表格格子。总表定位为**索引**,不复制各篇的论证,需要论证的地方链回原文。

正文取自上游的副本保持逐字不动,改动只限文首的代码库地址、行号基准说明和库内相对链接,以便按路径与上游比对。代码引用带文件名与行号,概率、准确率一类的数字标注来源 run 与 temperature。
