# typed-decision-models

搜集 **jev 类模型 / 类型化决策模型(typed decision model)** 的实现方法。

这类模型的共同点是:不把 LLM 当生成器用,而是把同一份权重当**分类器**读——一次前向、只取读位置的 logits、掩码到固定标签集、重归一化。于是输出被封闭在一个已知标签集上,没有文本需要解析,也没有东西可以幻觉。代表场景是 JevBench 式的"给定一段 state,在若干选项中选一个"。

二十一条路线可以放在一起读,分歧集中在「读位置怎么定、置信度从哪来」:

- **RYOTIDE**:零训练,把冻结 LLM 读成分类器——运行期标定读位置、掩码 + 重归一化,`marker_mass` 是它的诊断量;
- **Jeff**:在 RYOTIDE 那条读法之上**训一个决策头**,`slice_init_` 让训练起点逐位等于零样本读法;
- **Open-Jev**:把决策拆成 N 个 pointwise 的是非题,再训一个 `Yes − No` 播种的标量头读成校准打分;
- **Quyet**:在公开基座上自训权重(LLM 两条是 `gemma-4-31B-it` / `Qwen3.5-4B` 上合并 LoRA,encoder 三条是公开编码器 + 自训打分头),encoder 用 `[MASK]` 槽位、LLM 用字母 `A..J`,温度随权重一起发布;
- **Laya**:双向编码器,把决策改造成**填空题**——每个选项一个 `[MASK]` 槽位,一次前向读 K 个标量;顺序偏置在训练时用 `parallel` 布局消解,另有一个不跑模型的**路由器**逐请求挑 checkpoint;
- **SemIf-OpenJev**:同样零训练,但把读法工程化到**三个运行时 + 一个浏览器**,并配一条独立的校准链——读末位的字母槽位 `A`–`P`,顺序偏置不消除只度量(反转选项顺序翻转 10/36 的 argmax),浏览器那条路径是「**会生成 1 个 token**」这一侧的第一个例子;
- **OpenJev(HF)**:微调过的 27B + 一个挡在 vLLM 前面的 HTTP 补丁——读**第一个输出位置**上 52 个字母的 logits,训练把顺序偏置从 18.5% 压到 2.3%,而 T=0.85 / noul 的 (1.829074, 0) 是训练之后施加的常数,且**代码里的默认值与发布配方全都不同**;
- **vLLM Semantic Router**:不是一篇读法而是一个**运行时**——同一个 `/v1/decisions` 底下挂四代模型、四套读出协议(encoder 的 `[MASK]` 槽位 / decoder 的选项端点 / Vela 2.0 的八个标记 token / Decision 3.0 的 255 路答案码,其中它真的读末位)与四档数值 profile,`exact` 的目标是与发布包**逐字节相同**;Go 控制面拿到 typed answer 后**不用**模型报的 `confidence`,而是自己从 `probabilities` 重算一个,并拿 JevBench 标定自己的升级门;
- **CLM**:把决策整个换掉——不读 logits、没有词表,一次决策是**状态嵌入与候选嵌入的一次点积**;于是候选可以长期缓存、状态才需要现算,`marker_mass` 这类诊断量在这里没有对象,而**读位置被推给了编码器服务的池化默认值**(本仓不设定、不断言、不记录),整条链上也没有任何标定,`temperature` 只是每请求的入参且不回声。
- **Kev**:换掉的是「标签集从哪来」——**用户声明的每个选项就是一段 `<opt>…</opt>` 跨度**,骨干加载时直接丢掉 vocab head(`model.py:257`),所以既没有词表可以掩码、也没有「重归一化」这一步,softmax 落在头给出的恰好 K 个标量上;它付的代价是**必须训一个头**(`PointerHead` 的 q/k),换来的是候选集不受分词器约束、**读位置由 `encode` 在构造序列时算出来**因而运行期没有可标定的自由度;顺序偏置在训练期每 epoch 打散(外加一个构造性不变的开关 `option_isolation`,默认关且混合骨干不支持),运行期只度量、而**发布卡片不给翻转率**。
- **decider**:读法与 RYOTIDE 同源(标签行 logits → 掩码 → softmax),但**一次前向读 K 个槽位**——每题一个 `Answer k: (` 的左括号,全部落在同一行里,所以多问一题不改变任何已有答案;「typed」来自分词器里 **255 个单 token 标签**,而**同一个读法读两种权重**:自训的 0.8B–35B,以及不改权重、只靠一个 `decider_config.json` 的 chat 布局读进来的 stock 指令模型(后者在 Decision Index 上把自家训练的三个尺寸都压过);它把 RYOTIDE 的 `marker_mass` 变成了**概念不适用**——读出头就是 `lm_head` 的 255 个标签行,词表维度从不出现,标签外的质量在数学上不存在;置信度上有一处同名不同公式:`system_one()` 报 TypeSafe 的 rescale,`decide()` 报 `p_max`。
- **Nimble**:读法同样与 RYOTIDE 同源,但**一次前向只投影候选的那 K 行**(`full_vocabulary_projection: False`),所以「掩码 + 重归一化」在主路径上不存在;「typed」来自**按位置分配**的 26 个单 token 字母码(255 走另一套扩展编码器,且**已发布的托管端点只开到 26**);它把 RYOTIDE 的运行期标定换成了**训练期钉死**,代价是 **prompt 源码的 sha256 成了权重的一部分**——`schema_config.json` 里的 `prompt_code_sha256` 在加载、LoRA 合并、起服务三处各重算一次,不符即拒;它是二十一条里**唯一一份代码同时给出三个服务面、且三个面对 `output_tokens` 各说各话**的路线:本地 MLX/CUDA 两个 scorer 不生成任何 token,legacy `QwenEnumScorer` 走一次 1-token 解码,托管面则每 field 一个 token 外加一个丢弃的 warmup(3 题对应 `usage.output_tokens: 4`);顺序偏置**训练期打散、运行期连一次对照都没跑过**(工具在,`docs/PUBLIC_BENCHMARKS.md` 明说未测)。
- **Jevlike**:换掉的不是读法而是**两件更靠前的事**。①**链上没有 LLM**:默认骨干是从头训的字节嵌入(`nn.Embedding(257)`,`model.py:49`),可选路径是冻结编码器 + 掩码均值池化;②**标签集就是这一行的选项列表**——`label` 是行内下标(`data.py:30-31`),`cross_entropy` 直接落在这行的 N 个标量上,于是「标签必须单 token」「字母表上限」「候选数上限」三类约束同时**没有对象**;读法上它是**每个选项自己对 state 做一次注意力加权平均**(`model.py:34-42`),一次前向里两个 softmax(内层在 state 位置上、外层在选项上),所以「读位置」这个变量不存在,取而代之的是一张**逐选项的权重分布**——视觉侧把它量出来(归一化熵、peak、与敌人位置的相关、真实/空白/平均/打乱 patch 四组 KL,`audit.py:137-176`),**文本侧一个都没有**;置信度上它是继 CLM 之后第二条**零标定**路线,而且更彻底——全仓唯一的 `temperature` 是下棋时采样按键的旋钮(`examples/chess/eval.py:72-73`),连"每请求入参"这一层都没有;另外它是唯一一条**同一个头既读文本又读画面**的(8×10 个 patch、12 行共享控制器表、Doom 0–6 与象棋 7–11)。
- **H2O-Lightning**:读法与 RYOTIDE 同源,但它把「typed」从**构造**改成了**证明**——`serve_config.json` 里那 255 个标签里有 178 个是 BPE 片段(`in`、`the`、`ing`…),凭分词器根本保证不了单 token,所以 shim 在**首次请求**时用真实 prompt 逐个探针,要求 `tokenize(text + " " + 标签)` 恰好比 `tokenize(text)` 多一个 token 且 id 互异,不符即 503 拒服务(`h2o_lightning_shim.py:936-944`);读位置也不是标定出来的,而是 prompt 末尾那句字面量 `Answer:` 之后的那个位置(`:167-168`),运行期没有扫描、没有候选位置、没有阈值——标定被换成了**训练期钉死 + 加载期证明**。读数上它**只把候选的 K 个 token id 当请求参数发给 vLLM**(`logprob_token_ids`,:842-845),所以词表维度从不出现、`marker_mass` 概念不适用(与 decider / Nimble / Kev 同一个结论、第四种机制),代价是 255 个标签要分两次 completion(vLLM 单请求上限 128)。置信度是**读出来的**,但发布值被两个旋钮先后改写:逐题型温度(`choice 0.75 / noul 0.8 / score 0.65`,`serve_config.json:5`)与 yes/no 地板 `0.801`(`:6`,只抬不动 argmax,本文在 1,367 行上复算翻转 0 次),而这两个旋钮的来源会由 `/health` 如实回报(`noul_floor.source` / `temperature_source`,:1077-1078)——**改了数值的东西自己会说谁改的**。多问题共享 state 靠 vLLM 前缀缓存,shim 只把 `input_tokens` 的账单改对(共享头只计一次,:995-1001、:1059-1060);顺序偏置则是第三种状态:既不像 Kev 那样训练期打散、也不像 SemIf-OpenJev 那样反转一遍度量,**工具与度量都不在**(全仓对 `permut` / `shuffle` / `reorder` 零命中,部署者也没有可以自己跑一次对照的入口)。同一份代码里还有第二条服务面:带图的请求走 chat completions(assistant 轮用 `continue_final_message` 预填同一个 `Answer:`),外加一个**自带 SSRF 边界**的图像 URL 抓取器(只许公网 https、连到检查过的那个 IP、硬截止时间、先计数后抓取)。

属于第三种,而它是唯一一个**把这件事写成契约并让门去断言**的;metask-jev-rain 也落在机制层与字段层同时不成立这一侧,但方向相反——它**真的生成了探针 token,也真的把它们报了出来**,`usage.output_tokens` 不是被重新定义、也不是被硬编码,而是引擎生成量的实测值(其 §4、§10)。Clef 与 Kev CLM / Semantic Router 同类:`output_tokens: 0` 是响应组装处的字面量(`server.py:213`),机制与字段两个层面都成立;四个词里要改写两个——「只读最后一个位置」得说成「读池化档 `last` 选出的那一位,而那个位置由模板在 `enable_thinking=False` 下物化出来的空思考块定义」,「掩码到已知标签集」则没有对象(读出头只有 255 个分量,标签之外的质量在数学上不存在,其 §4.2、§5、§11)。它另有一处别家都没有:**注意力是非因果的**,于是这条读法在构造上不能有任何 KV cache——多问题共享 state 不是「不做」而是**做不到**(其 §4.1、§7)。metask-jev-rain 与这一组都不同,它把四个词里的**两个**都改写了,而且改写的方式在本族里是新的:**「只读最后一个位置」成立但「最后」由 chat 模板的尾巴定义**(模板在 `enable_thinking=False` 下吐出一个**空的、已闭合的**思考通道,读的就是紧跟它之后的那一位,`chat_template.jinja:381-386`);**「掩码到已知标签集」没有对象**——配置层有 neutral 白名单、引擎层 `raw_logprobs` 写死,读到的是未掩码分布上的真值,而「输出封闭」靠的是**只取标签那几个 token id 的 logprob**(与 decider / Nimble / Kev / H2O-Lightning / decisio / Clef / pplx-decider 同一结论、又一种机制);**「重归一化」存在但对象是标签**——同一标签的所有写法先 `logsumexp` 聚成一个分数,再按温度 softmax、加 1e-6 地板、重归一(`core.py:328-332`、`:356-362`);而**「一次前向」要按候选数分档**:26 个选项 1 次探针、676 个选项 22 次(其 §2、§4、§5、§10)。RSI-Jev 与 decisio 落在同一个 `output_tokens` 定义上(**题目数**,`app.py:162`,而 `wire.py:33-35` 的注释写着 *This path generates nothing at all*),所以它是「机制层成立、字段层不成立」的第二个例子、却是**第三种写法**——decisio 把这件事写成契约并让 C2 门断言,RSI-Jev 只是 `finish()` ## 收录约定

新增实现或案例时,在 `docs/<实现名>/` 下建目录,一事一文,并在上表登记一行。同一实现的文档放在同一子目录里,文件名直接写主题(如 `typed-decision-model.md`、`calibration.md`),不再重复实现名。

跨实现的总表放 `docs/` 顶层(如 `docs/comparison.md`),不进任何单个实现的子目录——它不属于某一个实现,且这样各篇更新时顶层只需改表格格子。总表定位为**索引**,不复制各篇的论证,需要论证的地方链回原文。

**外部基准与看板**的链接同样放 `docs/` 顶层,统一收在 [`docs/jev-benchmarks.md`](docs/jev-benchmarks.md):新增一条时在那里加一行(标题与自述取自页面自身,并记核验日期),README「外部基准」一节同步加一行。这类页面**不是实现**,不进上面的目录表;它们的分数据本仓一律不复制、不汇总、不跨页对比。

正文取自上游的副本保持逐字不动,改动只限文首的代码库地址、行号基准说明和库内相对链接,以便按路径与上游比对;**例外是核出的事实错误**——副本正文里被证伪的数字、基座档位、体量照改,并注明真值与来源,同步上游时这一处会显示为差异,属预期。代码引用带文件名与行号,概率、准确率一类的数字标注来源 run 与 temperature。

文档里关于**模型**的事实(基座是哪一档、参数量、权重体积、发布了哪些仓、钉的 revision)以 Hugging Face 的 API 与模型仓文件为准逐条核对,核对办法见 `.claude/skills/add-implementation/SKILL.md` 的步骤 5;抓下来的元数据快照不进仓库。
