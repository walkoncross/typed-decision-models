# typed-decision-models

搜集 **jev 类模型 / 类型化决策模型(typed decision model)** 的实现方法。

这类模型的共同点是:不把 LLM 当生成器用,而是把同一份权重当**分类器**读——一次前向、只取读位置的 logits、掩码到固定标签集、重归一化。于是输出被封闭在一个已知标签集上,没有文本需要解析,也没有东西可以幻觉。代表场景是 JevBench 式的"给定一段 state,在若干选项中选一个"。

十八条路线可以放在一起读,分歧集中在「读位置怎么定、置信度从哪来」:

- **RYOTIDE**:零训练,把冻结 LLM 读成分类器——运行期标定读位置、掩码 + 重归一化,`marker_mass` 是它的诊断量;
- **Jeff**:在 RYOTIDE 那条读法之上**训一个决策头**,`slice_init_` 让训练起点逐位等于零样本读法;
- **Open-Jev**:把决策拆成 N 个 pointwise 的是非题,再训一个 `Yes − No` 播种的标量头读成校准打分;
- **Quyet**:自训权重,encoder 用 `[MASK]` 槽位、LLM 用字母 `A..J`,温度随权重一起发布;
- **Laya**:双向编码器,把决策改造成**填空题**——每个选项一个 `[MASK]` 槽位,一次前向读 K 个标量;顺序偏置在训练时用 `parallel` 布局消解,另有一个不跑模型的**路由器**逐请求挑 checkpoint;
- **SemIf-OpenJev**:同样零训练,但把读法工程化到**三个运行时 + 一个浏览器**,并配一条独立的校准链——读末位的字母槽位 `A`–`P`,顺序偏置不消除只度量(反转选项顺序翻转 10/36 的 argmax),浏览器那条路径是「**会生成 1 个 token**」这一侧的第一个例子;
- **OpenJev(HF)**:微调过的 27B + 一个挡在 vLLM 前面的 HTTP 补丁——读**第一个输出位置**上 52 个字母的 logits,训练把顺序偏置从 18.5% 压到 2.3%,而 T=0.85 / noul 的 (1.829074, 0) 是训练之后施加的常数,且**代码里的默认值与发布配方全都不同**;
- **vLLM Semantic Router**:不是一篇读法而是一个**运行时**——同一个 `/v1/decisions` 底下挂三代模型、三套读出协议(encoder 的 `[MASK]` 槽位 / decoder 的选项端点 / Vela 2.0 的八个标记 token)与四档数值 profile,`exact` 的目标是与发布包**逐字节相同**;Go 控制面拿到 typed answer 后**不用**模型报的 `confidence`,而是自己从 `probabilities` 重算一个,并拿 JevBench 标定自己的升级门;
- **CLM**:把决策整个换掉——不读 logits、没有词表,一次决策是**状态嵌入与候选嵌入的一次点积**;于是候选可以长期缓存、状态才需要现算,`marker_mass` 这类诊断量在这里没有对象,而**读位置被推给了编码器服务的池化默认值**(本仓不设定、不断言、不记录),整条链上也没有任何标定,`temperature` 只是每请求的入参且不回声。
- **Kev**:换掉的是「标签集从哪来」——**用户声明的每个选项就是一段 `<opt>…</opt>` 跨度**,骨干加载时直接丢掉 vocab head(`model.py:257`),所以既没有词表可以掩码、也没有「重归一化」这一步,softmax 落在头给出的恰好 K 个标量上;它付的代价是**必须训一个头**(`PointerHead` 的 q/k),换来的是候选集不受分词器约束、**读位置由 `encode` 在构造序列时算出来**因而运行期没有可标定的自由度;顺序偏置在训练期每 epoch 打散(外加一个构造性不变的开关 `option_isolation`,默认关且混合骨干不支持),运行期只度量、而**发布卡片不给翻转率**。
- **decider**:读法与 RYOTIDE 同源(标签行 logits → 掩码 → softmax),但**一次前向读 K 个槽位**——每题一个 `Answer k: (` 的左括号,全部落在同一行里,所以多问一题不改变任何已有答案;「typed」来自分词器里 **255 个单 token 标签**,而**同一个读法读两种权重**:自训的 0.8B–35B,以及不改权重、只靠一个 `decider_config.json` 的 chat 布局读进来的 stock 指令模型(后者在 Decision Index 上把自家训练的三个尺寸都压过);它把 RYOTIDE 的 `marker_mass` 变成了**概念不适用**——读出头就是 `lm_head` 的 255 个标签行,词表维度从不出现,标签外的质量在数学上不存在;置信度上有一处同名不同公式:`system_one()` 报 TypeSafe 的 rescale,`decide()` 报 `p_max`。
- **Nimble**:读法同样与 RYOTIDE 同源,但**一次前向只投影候选的那 K 行**(`full_vocabulary_projection: False`),所以「掩码 + 重归一化」在主路径上不存在;「typed」来自**按位置分配**的 26 个单 token 字母码(255 走另一套扩展编码器,且**已发布的托管端点只开到 26**);它把 RYOTIDE 的运行期标定换成了**训练期钉死**,代价是 **prompt 源码的 sha256 成了权重的一部分**——`schema_config.json` 里的 `prompt_code_sha256` 在加载、LoRA 合并、起服务三处各重算一次,不符即拒;它是十八条里**唯一一份代码同时给出三个服务面、且三个面对 `output_tokens` 各说各话**的路线:本地 MLX/CUDA 两个 scorer 不生成任何 token,legacy `QwenEnumScorer` 走一次 1-token 解码,托管面则每 field 一个 token 外加一个丢弃的 warmup(3 题对应 `usage.output_tokens: 4`);顺序偏置**训练期打散、运行期连一次对照都没跑过**(工具在,`docs/PUBLIC_BENCHMARKS.md` 明说未测)。
- **Jevlike**:换掉的不是读法而是**两件更靠前的事**。①**链上没有 LLM**:默认骨干是从头训的字节嵌入(`nn.Embedding(257)`,`model.py:49`),可选路径是冻结编码器 + 掩码均值池化;②**标签集就是这一行的选项列表**——`label` 是行内下标(`data.py:30-31`),`cross_entropy` 直接落在这行的 N 个标量上,于是「标签必须单 token」「字母表上限」「候选数上限」三类约束同时**没有对象**;读法上它是**每个选项自己对 state 做一次注意力加权平均**(`model.py:34-42`),一次前向里两个 softmax(内层在 state 位置上、外层在选项上),所以「读位置」这个变量不存在,取而代之的是一张**逐选项的权重分布**——视觉侧把它量出来(归一化熵、peak、与敌人位置的相关、真实/空白/平均/打乱 patch 四组 KL,`audit.py:137-176`),**文本侧一个都没有**;置信度上它是继 CLM 之后第二条**零标定**路线,而且更彻底——全仓唯一的 `temperature` 是下棋时采样按键的旋钮(`examples/chess/eval.py:72-73`),连"每请求入参"这一层都没有;另外它是唯一一条**同一个头既读文本又读画面**的(8×10 个 patch、12 行共享控制器表、Doom 0–6 与象棋 7–11)。
- **H2O-Lightning**:读法与 RYOTIDE 同源,但它把「typed」从**构造**改成了**证明**——`serve_config.json` 里那 255 个标签里有 178 个是 BPE 片段(`in`、`the`、`ing`…),凭分词器根本保证不了单 token,所以 shim 在**首次请求**时用真实 prompt 逐个探针,要求 `tokenize(text + " " + 标签)` 恰好比 `tokenize(text)` 多一个 token 且 id 互异,不符即 503 拒服务(`h2o_lightning_shim.py:936-944`);读位置也不是标定出来的,而是 prompt 末尾那句字面量 `Answer:` 之后的那个位置(`:167-168`),运行期没有扫描、没有候选位置、没有阈值——标定被换成了**训练期钉死 + 加载期证明**。读数上它**只把候选的 K 个 token id 当请求参数发给 vLLM**(`logprob_token_ids`,:842-845),所以词表维度从不出现、`marker_mass` 概念不适用(与 decider / Nimble / Kev 同一个结论、第四种机制),代价是 255 个标签要分两次 completion(vLLM 单请求上限 128)。置信度是**读出来的**,但发布值被两个旋钮先后改写:逐题型温度(`choice 0.75 / noul 0.8 / score 0.65`,`serve_config.json:5`)与 yes/no 地板 `0.801`(`:6`,只抬不动 argmax,本文在 1,367 行上复算翻转 0 次),而这两个旋钮的来源会由 `/health` 如实回报(`noul_floor.source` / `temperature_source`,:1077-1078)——**改了数值的东西自己会说谁改的**。多问题共享 state 靠 vLLM 前缀缓存,shim 只把 `input_tokens` 的账单改对(共享头只计一次,:995-1001、:1059-1060);顺序偏置则是第三种状态:既不像 Kev 那样训练期打散、也不像 SemIf-OpenJev 那样反转一遍度量,**工具与度量都不在**(全仓对 `permut` / `shuffle` / `reorder` 零命中,部署者也没有可以自己跑一次对照的入口)。同一份代码里还有第二条服务面:带图的请求走 chat completions(assistant 轮用 `continue_final_message` 预填同一个 `Answer:`),外加一个**自带 SSRF 边界**的图像 URL 抓取器(只许公网 https、连到检查过的那个 IP、硬截止时间、先计数后抓取)。
- **decisio**:读法与 RYOTIDE 同源,但它把两个变量都从「训练期固定」推到了「**构造期算出来 + 加载期断言**」。①**标签集是运行期产物**:`letter_labels(tok, K)` 每次现取前 K 个「加前导空格后恰好单 token」的字母码(`letters.py:73-87`),凑不够就抛,所以 **K 在同一条 committed 产物里逐题不同**(实测 K ∈ {3,4,5,6,7,8,9,10,77,151}),而 255 这个上限是**线格式的 8 位选项下标**(`letters.py:28`)而不是分词器的上限;②**掩码不由代码做**——`allowed_token_ids` 是请求参数、`logprobs_mode="processed_logprobs"` 在引擎构建时设死(`vllm_engine.py:277`、`:543-544`),返回的 K 个数在构造上就是这 K 行上的 log-softmax,所以 `marker_mass` **概念不适用**(与 decider / Nimble / Kev / H2O-Lightning 同一个结论、第五种机制);③它是十八条里**唯一一篇同一个读法同时服务三个基座、两条路由给不同的数、还带三道一致性门**的走查——`/v1/answer` 是**未加温度**的原生读数、`/v1/systemone` 是按**逐题型温度**加过权的,而 **C4 门在比较前显式把温度补回去**(`systemone_conformance.py:318-335`,`max_abs_delta_p == 0.0` 且翻转 0 才算过);④三个基座画像是 `PromptFormat` 四个开关(`tail` / `slot` / `variants` / `system_prompt`,`letters.py:195-242`)加逐 base 的填充、温度与边界注册策略,**布局进任务指纹**——换布局之后注册过的任务**静默不生效**,只在启动日志里一条 WARNING(`vllm_engine.py:1676-1678`);⑤多问题共享 state 拆成三件可观测的机件(前缀按 token 空间切、按块边界填充、答案发出后再把 state 边界注册进缓存,`serve/boundary.py`),并且**填充位置是被测量过的自由度**——`between` 那个位置 *moved 9.4% of top answers against the unpadded prompt*(`vllm_engine.py:122-124`),committed 的 `runs/2026-10-02_pad-policy-row/conformance_l1.json.gz` 是 C4 门**唯一一条 FAIL**,max |Δp| = 0.0147、翻转 0;⑥`usage.output_tokens` 被定义成**题目数**(`systemone.py:600`,`docs/api.md:77` 写成契约、C2 门断言),而 separate 模式下**恰好**等于真采的 token 数,packed / CPU 替身 / MLX 三种情况**一个 token 都不生成**却照报同一个数。
- **Clef**:换掉的不是读位置、也不是标签表,而是**把这两件事合并成同一段自造文本**。①请求里的 `criteria` 被渲染成 prompt 中段的 `SCHEMA FIELDS:` 段(`joint_schema_model.py:110`、`:116`、`:130`),头再按这段文本**自己的 token 下标区间**去池化——`question_span` 与 `option_spans` 是在拼 prompt 时算出来的(`:119`、`:136`、`:171-187`),于是「这个选项是什么」与「去哪里读它」是同一个下标的两种说法;②**于是选项不必单 token**:本文用发布的 `tokenizer.json` 实测 `overdue` 是 **2 个 token**(`[1908, 22906]`),而 255 / 52 / 26 / 16 这些上限量的是「从词表里挑标签」的容量,这条链上没有这件事;③**「不物化词表维度」只半成立**:头从不把 hidden state 投影到 248,320 维上(所以 `marker_mass` 概念不适用、第六种机制),但 `output_embedding_weight[token_ids].mean(0)`(`:381-382`)确实读了词表矩阵的**若干行**——当嵌入用,从不当 logits 用;④**置信度是两项之和**:`logit = prior + σ(g)·joint`,其中 `prior` 只有 **1 个可训练参数**(`prior_logit_scale`),它量的就是「选项文本的词嵌入均值」与「问题向量 + 全序列末位」的余弦(`:433-439`)——**RYOTIDE 那条零样本读法没有被丢掉,它成了头里的一个加数**,与 Jeff 的 `slice_init_`(把训练起点对到零样本读法)恰成对照;实测发布权重里两个尺度**逐位相同**(bf16 2.296875 → `exp` 9.94306)、门是 `sigmoid(−2.0) = 0.119203`(其 §15.2);⑤顺序偏置是**第三种处置**:`choice` 的选项在**渲染期按 id 排序**(`:56`),调用方的顺序根本进不了 prompt,而 `score` 必须保序(下标就是档位)——仓里对顺序偏置**没有任何度量、也没有对照入口**;⑥多问题不是「共享前缀」而是**联合解码**:4 层 decoder 在 `fields` 之间做自注意力(`:421-424`),所以删掉某一题,剩下题目的答案**可以变**——这是十八条里唯一一条题与题互相可见的路线;⑦守卫是十八条里**最薄**的:没有 `/health`、没有 `/v1/version`、没有 prompt 哈希、没有 HTTP 服务器(HTTP 层在 SGLang 的 `dev-clef` 镜像里),而 `systemone()` 回声的 `"model": request["model"]`(`:573`)是**调用方自己发的字符串**——schema 的排版是这个头的权重契约,而发布物里**没有任何东西把这份契约记下来**(对照 Nimble 把 prompt 源码的 sha256 钉进 `schema_config.json`);⑧它还留着一条**静默截断**:state 超出 `max_length` 时从右端截掉、不报告(`:170`),而 schema 段本身太长则是抛错(`:166-169`)——该响的响、该静默的静默。
- **pplx-decider**:读法与 RYOTIDE 同源(标签行 logits → 掩码 → softmax),但它换掉的是**词表之外那件事**。①**读出头不是 `lm_head`**——检查点索引里 1,183 个张量、`lm_head` 一个键都没有,那 255 行被落成 `readout.safetensors` **单独发布**(从基座起训时才从 `lm_head.weight[token_ids]` gather 出来,`model.py:250`),所以词表维度从不出现、`marker_mass` **概念不适用**(与 decider / Nimble / Kev / H2O-Lightning / decisio / Clef 同一个结论、**第九种机制**);②**全注意力层被显式掀掉因果掩码**(`attention_mode: "noncausal_full_attention"`,钩子把掩码换成只有 padding 的那一份,`model.py:50-55`),这是十八条里没有第二条做过的事,代价是 **KV cache 被构造性拒绝**(`model.py:38-39` 直接抛),于是多问题共享 state 不是「不做」而是**做不到**,`input_tokens` 老老实实按重复编码计费;③**「typed」来自分词器,而发布配置里那份码表是校验**——702 个候选中筛出 588 个能单 token 化的、取前 255 个、末位落在 `JT`,而 `KA`–`ZZ` 之间还有 333 个合格的**永远不会被用到**(本文在随仓 `tokenizer.json` 上重算,与 `decision_config.json` 逐项相同);④**图像与文本走同一条读法**(图像占位拼在 user 轮开头,`model.py:106`),不是第二条服务面,而发布代码的默认图上限 **2048×2048** 落在训练与评测用的 **512×512** 之外(`README:107-110`);⑤顺序偏置**训练期每 step 打散**(`train.py:976`,种子按 step 派生)、运行期保序,而**度量与工具同时缺席**;⑥温度是**一个全局值**(`1.0087417621345625`),由 983 行温度折上黄金分割拟合并**自动落盘、无接受 / 拒绝判据**;服务面报的 `confidence` 是**改写过**的 `(p_max − 1/k)/(1 − 1/k)`(低于 1/k 一律截到 0),而评测记录里的 `confidence` 是**未改写的 `p_max`**;⑦`GET /` 读一个**不在发布的 48 个文件里**的 `playground.html`(`server.py:162`),是这份发布里唯一一处「路由指着的东西没写」。

必须为空」五道门(`launch.py:140-149`、`:192-213`、`:279-282`);而**一个永不使用 draft 路径的部署仍然必须能把 draft 路径建起来**(热身里跑一次、`supports_slow_session` 必须为真)。顺序偏置在服务侧**不存在该变量**,唯一的对照臂是维护者工具的一个开关,而且**不随包发布结果**(`bench.py:156`、`:547-548`),发布的那份校准也只能来自 `criteria` 顺序的那一轮(`bench.py:554`)。

共同底线只有一条,也是 RYOTIDE 第 13 节那四条不变量的来源:**一次前向、只读最后一个位置、掩码到已知标签集、重归一化,`output_tokens = 0`**。违反时数字会看似合理却是错的——十八条路线都在同一个主题上记录了各自的踩坑方式。两处例外都在「会生成 1 个 token」这一侧:SemIf-OpenJev 的浏览器路径用一次 1-token 的解码换一个能返回 logprobs 的接口,读的仍是被迫输出的那个 token 的 `top_logprobs`(其 §9);OpenJev(HF) 对 vLLM 发 `max_tokens: 1`,而响应里 `output_tokens: 0` 是**硬编码**的(其 §4)。Semantic Router 是这条底线上**最干净**的一条:`output_tokens` 在响应组装处硬编码为 0(其 §2.2),三套读法没有一条会生成 token。CLM 是另一头的极端:它连「一次前向」都不必改写——决策本身没有前向,`output_tokens: 0` 是字面量(其 §4),四个词里只剩「输出封闭在已知选项集上」还需要讲,而它靠的是**根本没有词表可越界**(其 §2.2)。Kev 是**字段层面唯一不成立**的一条:它确实不生成 token,但 `usage.output_tokens` 被定义成「序列化后答案 JSON 的 token 数」(`api.py:163-165`,README 第 284 行明说 *counts tokens in the serialized answers, not generated tokens*)——机制层面成立,字段层面不成立(其 §9.4);同时它也是第一条**连「掩码 + 重归一化」都不存在**的路线,所以那四个词在它身上只剩「一次前向」与「输出封闭在选项集上」。decider 与 Semantic Router 同类——`output_tokens: 0` 在它的三个服务与库入口都是响应组装处的字面量(其 §4.4、§9),而它唯一的例外也在「1 个 token」这一侧:`serve_vllm` 向 vLLM 发 `max_tokens=1, temperature=0.0, logprob_token_ids`,只为拿回那个位置的 logprobs,**不消费**采样结果(其 §4.4)。Nimble 是十八条里**同一份代码库内部就自相矛盾**的一条:本地两个 scorer 连「生成」这个概念都没有(统计里不存在 output token 这个字段),legacy `QwenEnumScorer` 走 `max_new_tokens=1` 的真解码(`enum_scorer.py:119`),而托管面是 SGLang 上**每 field 一个 token 外加一个丢弃的 warmup**——committed 的两次托管 smoke 记录里,3 个 field 的 `usage.output_tokens` 都是 **4**(其 §1、§13.3),上游文档也照写 *This is not a zero-generation backend*。所以引用 Nimble 的 `output_tokens` 之前,**先确认问的是哪个服务面**——这不是口径不同,是三个不同的入口。Jevlike 又是另一头的极端:它**没有服务、没有 `usage` 字段、也没有 token 计数这回事**(其 §8),四个词里只剩「一次前向」与「输出封闭在选项集上」还字面成立——**「掩码到已知标签集」与「重归一化」在这条链上都没有对象**(头只输出 K 个标量),而「只读最后一个位置」要改写成「每个选项自己对全部未掩位置做一次加权平均」(其 §4、§10)。H2O-Lightning 是这条底线上**最干净**的一条:`output_tokens: 0` 在响应组装处是字面量(`h2o_lightning_shim.py:1067`),图像路径也走同一个 `respond()`,所以两条服务面都是 0(其 §13);但另外三个词要改写——「只读最后一个位置」得说成「读渲染后 prompt 的下一位,而那个位置由末尾的字面量 `Answer:` 定义」,「掩码到已知标签集」则没有对象(候选 token id 是请求参数,词表维度从不出现,其 §5、§13)。decisio 是**字段层面第二个不按「0」写的一条**,而且它的定义与 Kev 完全不同:`usage.output_tokens` 被定义成**题目数**(`systemone.py:600`,`docs/api.md:77` 明写 *`usage.output_tokens` is one per question*,C2 门断言 `r.usage.output_tokens == len(questions)`)。巧合之处在于 separate 模式下**每题确实采了一个 token**(`max_tokens=1`,只为拿回那个位置的 logprobs,采到的 token 从不被读),所以这个数在那个模式下恰好等于真实生成量;而 **packed 模式走池化 runner 一个 token 都不生成**、CPU 替身与 MLX 也不生成,三者仍然报同一个数(其 §4、§15.2)。所以「底线是 `output_tokens = 0`」这句话在十八条里要分三种问法:是**机制层**不成立(Kev:字段被定义成序列化答案的 token 数)、是**字段层**不成立(OpenJev(HF):硬编码 0 而实际采了 1 个)、还是**两者都不成立**——decisio 属于第三种,而它是唯一一个**把这件事写成契约并让门去断言**的;metask-jev-rain 也落在机制层与字段层同时不成立这一侧,但方向相反——它**真的生成了探针 token,也真的把它们报了出来**,`usage.output_tokens` 不是被重新定义、也不是被硬编码,而是引擎生成量的实测值(其 §4、§10)。Clef 与 Kev 一样落在**机制层成立、字段层不成立**这一侧,但方向相反:Kev 是把那个 0 换成一个有定义的数,Clef 是把 0 写死在响应组装处(`joint_schema_model.py:575`)——它连「生成」这条路径都没有,骨干一次前向、头输出 K 个标量,`max_tokens`、采样器、`logprob_token_ids` 这些词在整份代码里一个都不出现。pplx-decider 与 CLM / Semantic Router 同类:`output_tokens: 0` 是响应组装处的字面量(`server.py:213`),机制与字段两个层面都成立;四个词里要改写两个——「只读最后一个位置」得说成「读池化档 `last` 选出的那一位,而那个位置由模板在 `enable_thinking=False` 下物化出来的空思考块定义」,「掩码到已知标签集」则没有对象(读出头只有 255 个分量,标签之外的质量在数学上不存在,其 §4.2、§5、§11)。它另有一处别家都没有:**注意力是非因果的**,于是这条读法在构造上不能有任何 KV cache——多问题共享 state 不是「不做」而是**做不到**(其 §4.1、§7)。metask-jev-rain 与这一组都不同,它把四个词里的**两个**都改写了,而且改写的方式在本族里是新的:**「只读最后一个位置」成立但「最后」由 chat 模板的尾巴定义**(模板在 `enable_thinking=False` 下吐出一个**空的、已闭合的**思考通道,读的就是紧跟它之后的那一位,`chat_template.jinja:381-386`);**「掩码到已知标签集」没有对象**——配置层有 neutral 白名单、引擎层 `raw_logprobs` 写死,读到的是未掩码分布上的真值,而「输出封闭」靠的是**只取标签那几个 token id 的 logprob**(与 decider / Nimble / Kev / H2O-Lightning / decisio / Clef / pplx-decider 同一结论、又一种机制);**「重归一化」存在但对象是标签**——同一标签的所有写法先 `logsumexp` 聚成一个分数,再按温度 softmax、加 1e-6 地板、重归一(`core.py:328-332`、`:356-362`);而**「一次前向」要按候选数分档**:26 个选项 1 次探针、676 个选项 22 次(其 §2、§4、§5、§10)。

## 收录约定

新增实现或案例时,在 `docs/<实现名>/` 下建目录,一事一文,并在上表登记一行。同一实现的文档放在同一子目录里,文件名直接写主题(如 `typed-decision-model.md`、`calibration.md`),不再重复实现名。

跨实现的总表放 `docs/` 顶层(如 `docs/comparison.md`),不进任何单个实现的子目录——它不属于某一个实现,且这样各篇更新时顶层只需改表格格子。总表定位为**索引**,不复制各篇的论证,需要论证的地方链回原文。

正文取自上游的副本保持逐字不动,改动只限文首的代码库地址、行号基准说明和库内相对链接,以便按路径与上游比对。代码引用带文件名与行号,概率、准确率一类的数字标注来源 run 与 temperature。
