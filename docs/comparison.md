# 十五条路线对照总表

> 本文是**索引与总表**，不是又一篇走查：只放跨实现才看得见的对照，论证留在各篇里。
> 需要细节时按文中的节号回到对应文档，本文不重复它们的推理过程。

收录的十五条路线，各自有一篇逐环节走查：

| 实现 | 走查 | 一句话 |
|---|---|---|
| RYOTIDE | [`ryotide/typed-decision-model.md`](ryotide/typed-decision-model.md) | 零训练，把冻结 LLM **读**成分类器 |
| Jeff | [`jeff-serve/typed-decision-model.md`](jeff-serve/typed-decision-model.md) | 在 RYOTIDE 那条读法之上**训**一个决策头 |

| Laya | [`laya/typed-decision-model.md`](laya/typed-decision-model.md) | 双向编码器，把决策做成**填空题**：每选项一个 `[MASK]` 槽位 |
| SemIf-OpenJev | [`semif-openjev/typed-decision-model.md`](semif-openjev/typed-decision-model.md) | 零训练，读末位的**字母槽位** `A`–`P`；把读法铺到三个运行时 + 一个浏览器 |
| OpenJev(HF) | [`openjev-hf/typed-decision-model.md`](openjev-hf/typed-decision-model.md) | 微调过的 27B + 一个 vLLM 前面的 HTTP 补丁：读**第一个输出位置**上的 52 个字母 |

| CLM | [`clm/typed-decision-model.md`](clm/typed-decision-model.md) | 一次决策 = **状态嵌入与候选嵌入的一次点积**：没有词表、没有掩码，读位置被推给编码器的池化默认值，整条链上没有标定 |
| Kev | [`kev/typed-decision-model.md`](kev/typed-decision-model.md) | 请求声明的每个选项就是一段 `<opt>…</opt>` 跨度，**词表整个不参与**（骨干连 vocab head 都不加载）；softmax 直接落在头给出的 K 个标量上，没有掩码也没有重归一化 |
| decider | [`decider/typed-decision-model.md`](decider/typed-decision-model.md) | 读法与 RYOTIDE 同源，但**一次前向读 K 个 `Answer k: (` 槽位**；「typed」靠分词器里 255 个单 token 标签，而**同一个读法读两种权重**（自训 0.8B–35B，与不改权重只靠一个 chat 布局配置读进来的 stock 指令模型） |
| Nimble | [`nimble/typed-decision-model.md`](nimble/typed-decision-model.md) | 读法同源，但**只投影候选的那 K 行**（词表维度从不出现）；「typed」靠**按位置分配**的 26 个字母码；把 RYOTIDE 的运行期标定换成**训练期钉死**，代价是 **prompt 源码的 sha256 成了权重的一部分**；一份代码里同时有**三个服务面**，三个对 `output_tokens` 的说法各不相同 |
| Jevlike | [`jevlike/typed-decision-model.md`](jevlike/typed-decision-model.md) | 链上**没有 LLM**：从头训的字节嵌入，或冻结编码器 + 一个注意力头；**标签集就是这一行的选项列表**，于是单 token 约束 / 字母表 / 候选数上限同时消失；读法是**每个选项自己对 state 做一次加权平均**，没有「位置」可读 |
| H2O-Lightning | [`h2o-lightning/typed-decision-model.md`](h2o-lightning/typed-decision-model.md) | 一次决策 = **一次 1-token 前向 + 候选那 K 个 token id 的 logprob**：候选 id 是**请求参数**，词表维度从不出现，于是没有掩码这一步；「typed」靠 **255 个标签的加载期逐标签探针**证明，「读位置」靠 prompt 末尾那句字面量 `Answer:` 钉住——代价是换分词器或换布局就让服务 **503 拒起** |
| decisio | [`decisio/typed-decision-model.md`](decisio/typed-decision-model.md) | 零训练，把冻结基座读成**字母分类器**；标签集是**运行期从分词器推出来的**，同一条读法服务三个基座、两条路由给不同的数，多问题共享 state 拆成三件可观测的机件 |

共同底线原本写作两条：**一次前向**、**不生成任何 token（`output_tokens = 0`）**，以及**输出封闭在已知选项集上**。
两处例外都在「确实采了一个 token」这一侧：SemIf-OpenJev 的浏览器路径用 `max_tokens: 1` 换来一个能返回
logprobs 的接口，读的仍是被迫输出的那一个 token 的 `top_logprobs`，而不是采样结果（其 §9）；
OpenJev(HF) 对 vLLM 发 `max_tokens: 1`，响应里 `"output_tokens": 0` 是**硬编码**的（`shim.py:325`，其 §4）。
所以更准确的说法是 **「不靠解析生成文本来得到分数」**：十五条都满足这一条。SemIf-OpenJev 的浏览器演示页
与 OpenJev(HF) 的 `/v1/chat/completions` 都另有生成通道，但那是各自立起来当对照或透传的东西，不是读法。
vLLM Semantic Router 是这一条上最干净的一条：`output_tokens: 0` 是在**响应组装处**硬编码的
（`runtime.py:961-963`，其 §2.2），三套读法没有一条会生成 token。
CLM 是另一头的极端：它连「一次前向」都不必改写，因为**决策本身没有前向**——`output_tokens: 0`
是 `engine.py:138` 的字面量，四个词里只剩「输出封闭在已知选项集上」还需要讲，
而它靠的是**根本没有词表可以越界**（其 §2.2、§4.3）。
Kev 是**字段层面唯一不成立**的一条：它确实不生成 token（读法只有一次前向），但 `usage.output_tokens`
被定义成**序列化后答案 JSON 的 token 数**（`api.py:163-165`，README 第 284 行明说 *counts tokens in the
serialized answers, not generated tokens*）。所以引用「`output_tokens = 0`」这条底线时，除 Kev 与 decisio 外的十三条都可以按
「机制 / 字段」两个层面分别成立，Kev 只在机制层面成立（其 §9.4、本文 §5 第 9 条），
decisio 则两个层面都不按「0」写——它把字段**定义成题目数**（本文 §5 第 15 条）。Nimble 是另一类麻烦：
它**同一份代码库里三个服务面对同一个问题给出三种答案**——本地两个 scorer 连「output token」这个字段都不存在，
legacy `QwenEnumScorer` 走 `max_new_tokens=1` 的真解码，托管面则是每 field 一个 token 加一个丢弃的 warmup
（3 个 field → `usage.output_tokens: 4`，其 §1、§13.3）。所以它不违反底线，但**引用它的 `output_tokens` 之前
必须先问是哪个入口**——这与「同一个字段名在不同代际是两个公式」同类，只是这里的分歧在同一份代码内部。
decisio 是同类麻烦的**第二种成因**：它**只有一个入口、一个定义**，而那个定义是「**答案的个数**」而不是
「生成的 token 数」——`usage.output_tokens = len(questions)`（`systemone.py:600`），`docs/api.md:77`
把它写成契约、C2 门断言它（`systemone_conformance.py:182`）。于是同一个数在 separate 模式下**恰好**等于
真采的 token 数（每题 `max_tokens=1`，只为拿回那个位置的 logprobs），而在 packed / CPU 替身 / MLX
三种模式下一个 token 都不生成——**定义没说错，是名字与直觉不符**（其 §4、§15.2）。
Jevlike 又是另一头：它**没有服务、没有 `usage` 字段、也没有任何 token 计数**（其 §8），
所以「`output_tokens = 0`」这句话在它身上没有落点——四条底线词里只剩「一次前向」与「输出封闭在选项集上」
字面成立，「掩码到已知标签集」与「重归一化」没有对象，「只读最后一个位置」要改写（其 §2.1、§4、§5）。

> 「只读最后一个位置」**不是**共同底线。十五条里 RYOTIDE、Jeff、Open-Jev、OpenJev(HF) 与 Nimble 读末位
> （最后一者的「末位」是**第一个输出位置**，在因果 LM 里是同一个分布，差别在它靠微调把语义搬到那里，其 §3）；
> Quyet 的 encoder 路径、Laya 与 Kev 读的是各选项自己的槽位/端点（各一篇的 §5 / §4 / §3），decider 读的是**每题一个、由 prompt 构造出来的槽位**（K 个位置，既不是末位、也不是逐选项，其 §3）。SemIf-OpenJev 两条都算：
> `direct` / `serial` / `mlx` 读末位，但 `shared` 模式读的是**每条序列自己**的末位——批内有 padding 时
> 与 `-1` 不是同一个位置（其 §7.3）。vLLM Semantic Router 里这条更要按 runtime 分：encoder 读 K 个
> `[MASK]` 槽位，decoder 读 K 个选项端点 + 1 个 query 行，Vela 2.0 读每题若干个标记（其 §4）。
> CLM 则把这个变量**整个拿掉了**：决策读的是 K+1 个向量、做的是 K 次点积，没有位置可读；
> 「最后一个位置」只留在编码器的池化里，而那个选择不在它的仓库里（其 §3.3）。
> 差别集中在**读哪个位置**和**置信度从哪来**——而 CLM 对第一个问题的回答是「不归我管」，
> Kev 的回答是「位置我自己拼，所以它不可能落错」，decider 的回答是「位置在 prompt 构造时写死，
> 运行期没有可标定的自由度」，Nimble 的回答是同一句话的**加强版**——位置也是构造出来的末位，
> 但它把「prompt 长什么样」本身写进了权重契约（`prompt_code_sha256`），于是**位置正确性不再依赖运行期检查，
> 而依赖权重与代码是不是同一版**（其 §3、§10 新增 1）——decisio 的回答是 decider 那句话的**扩展版**：
> 「位置在 prompt 构造时写死（`answer_slot` 一个开关，`letters.py:285`），运行期没有可标定的自由度」，
> 而且**连标签集也是运行期现算的**——前 K 个能加前导空格单 token 的字母码（`letters.py:57-70`），
> 所以它连「一张可被训练固定的标签表」都没有（其 §2、§3、§7）——而 Jevlike 的回答是**这个问题没有对象**：
> 它读的不是一个位置，而是**每个选项各自对全部 state 位置的一次加权平均**，「读得对不对」因此换成了
> 「这张权重分布是不是非均匀、是不是跟着任务变量走」（其 §3、§4；视觉侧量它、文本侧不量）。

### 温度的代价，十五条记录七种表现

- RYOTIDE §12(f)：同一条记录顶部概率 T=1 时 **0.999917**、T=1.924 时 **0.981007**；
- Open-Jev §10(i)：255 候选下顶部概率 T=1.736 时 **0.107047**、还原 T=1 后 **0.575983**（T>1 的压平效应随候选数放大）；
- Jeff §9.1：100000 组随机 `(p, T)` 中 argmax **改变 0 次**——温度不改准确率，所以能被单独拟合与事后报告；
- Laya §10.3：`choice:11+` 的 **0.1006** 会把真实的 0.24 发布成 **0.99**，clamp 到 `TEMP_MIN=0.5` 之后仍发布成 **0.4993**——源码原话是 *The clamp bounds the damage; it does not calibrate anything*；
- 而 Jeff 多一项 `noul_edge`：`0.7999 → 0.801`，`0.8001 → 0.8001`，**raw 更大报出去更小**，跨样本比较被它改写的 P(yes) 不可靠；
- SemIf-OpenJev §12：同一批 144 行，T=1 时平均 top-1 是 **0.8628**、T=1.2342 时是 **0.8333**，argmax 翻转 **0 次**——这正是「零训练 ⇒ 温度只动置信度」的实证；而它逐 workload 的三个 T 相差一倍以上（1.2342 vs 2.4990），**拿错哪一个都会得到看似合理的错数**；
- OpenJev(HF) §5/§13：T 与 noul 斜率是**在 `READOUT_TARGETED=1` 下拟合**的，而那个开关的**文件默认是关的**（`shim.py:21`）；默认关时读数协议换成 `top_logprobs` + 掉出 top-K 给 `−30.0` 兜底（`shim.py:164`）。所以「跑起来看着正常」的那套默认，用的是**为另一套读数拟合的常数**；
- vLLM Semantic Router §5.3/§10.1：**温度在这个仓里是逐 runtime 而不是逐模型的**。同一个 `decision1` 家族、同一个 golden 文件里，Kai / Lex / Route 走的 encoder 路径**不经过任何温度**（包不许带标定），Eos / Sol / Nox / Lux 走的 decoder 路径**必经温度**。所以拿 Kai 的 `probabilities` 与 Eos 的 `probabilities` 并排比较，比的是一条未校准分布与一条校准分布——而它们的字段名、字段形状、来源文件都一模一样；
- Jevlike §9.3：**这一条没有温度可谈**，但它把「采样还是贪心」做成了接口层的选择——`--sample [T]`（`examples/chess/eval.py:264-265`），而实测方向与直觉相反：**贪心按键远差于采样**，一个 checkpoint 中途有 **68%** 的回合撞上 40 键预算（`examples/chess/README.md:78`）。原因是屏幕是唯一的状态，一个不改变屏幕的按键（或两个互相抵消的按键）会无限循环。这条数字只写在**文档**里、没有随仓提交任何记录，本文未复算（其 §9.3）。这是第五种表现：**温度这个变量本身不存在，而采样旋钮确实在改行为**。
- CLM §10.2/§14.1：**这一条的 T 根本不在产物里**。别家至少能列出一个数（或说明「值在包里」），CLM 只能说明「它是入参、默认 1.0、不回声」。所以它的每一份 committed 记录都带着一个**靠反推才成立的 T**：那批 T-Rex 数字能定下 T=1.0，理由是请求体里没有这个键（`backends.py:127-129`）加服务端默认 1.0（`server.py:106`）——而不是因为记录里写了。CLM 与 Jevlike 是十四条里仅有的两条**根本没有「训练之后施加的常数」**的路线——
区别在 CLM 至少有一个每请求的入参（默认 1.0、不回声），而 Jevlike **连入参都没有**，分布就是 `softmax(logits)` 原样（其 §9.1）。
- Kev §6.4/§13.3：**这一条的 T 进了记录，而且方向与直觉相反**。落盘的 `logits` 是**已经被温度除过**的（`predictors.py:140-141`），所以要还原原始 logits 得**乘**回 T（`metrics.py:241`）——别的实现里「`logits` 就是原始 logits」这个直觉在这里是错的。实测：发布检查点的 2 行 `rows.json` 里 `p` 与 `softmax(logits)` 差 ≤ **1.5e-08**（4B，T=2.406050072164233），把 `logits` 当原始值去算 `softmax(logits/T)` 会得到一条完全不同的、更平的分布（最大差 **0.68**）。同一条路线上另一件事恰成对照：**温度不动 argmax，选项顺序动**——发布的 9B 读数在 T=2.1936 下选项顺序把平均最大概率挪了 **0.0681**、翻转 **2/36** 的 argmax（`runs/rel9-public/1-jaredpalmer_kev-9b/report.json`），而 27B 是 0/36。这两列在 Kev 的记录里是分开的。
- decider §14.1：**这一条把温度律本身做成了可复算的**。在 committed 的 `tests/data/temperature_1_3_0_pins.json` 上重算：把 T=1 那一列的概率取对数当 logits、除以 1.935 再 softmax，能**逐位复现**已存盘的 `t1.935` 列（最大偏差 **~2e-8**）；同时 argmax 在四个温度下**翻转 0 次**、每行概率和仍是 1。所以「温度就是 `logits / T`、而且只动数值」在这里不是文档里的说法，而是**能在产物上验证的**。代价要说清楚：那批数字来自一个 **16 维的确定性替身骨干**（`tests/temperature_cases.py:17-51`），与任何发布的 `decider-*` 权重无关，它证明的是读数链的内部一致，不是模型质量。
- Nimble §9.2/§13.1：**这一条把「温度只动数值」从数学性质变成了代码事实**——`argmax` 取的是 `row`（原始 logits）而不是 `softmax(row/T)`（`parallel_scorer.py:178-180`、`cuda_scorer.py:146-147`），于是哪怕温度是负数（构造期已拒绝）都不会改选择路径。代价方向与别家相反：**同一次拟合不是全面变好**——log loss 与 Brier 都降（0.692→0.555、0.348→0.295），但 holdout 上 ECE 从 **0.052 抬到 0.054**、64 道 rating 题从 **0.105 抬到 0.177**，「一个标量温度不可能同时修好所有题型」在这里留了记录。另有一条**只按哈希认身份**的坑：revision 传短哈希 `93ec5d6` 不匹配、**静默**落到 T=1.0，拿到的是未校准概率而没有任何报错（`docs/PARALLEL_SCORING.md` 明写这一点）。
- H2O-Lightning §16：**这一条的温度不是拟合出来的，所以「确认 T」确认的是一份配置而不是一次实验**。发布值是 `choice 0.75 / noul 0.8 / score 0.65`，而它在同一条链上有一个**作用相反**的伙伴：yes/no 地板 0.801。两者都改发布数值、都不改 argmax（地板在 1,367 行 noul 上复算翻转 **0 次**），但地板会把 t=0.8 这一档的升级率从 **41.0 %** 抹成 **0.0 %**——**同一张阈值表在出厂配置下不可用**。这不是精度问题，是信号被抹平：出厂配置下没有一条 yes/no 会被判为「不确定」。另有一处口径：卡片的「text temperature 0.8」只对 `noul` 成立。
- decisio §14.1：**这一条把温度律做成了可逐位复算的**，而且复算的产物是它自己的 committed 读数。`runs/2026-09-30_served-default/decision_index/` 下有一对 run：`temperature_1`（T 关）与 `default`（T 取同目录 `health_default.json` 里的 **1.307**），各 20,810 行、`run_id` 集合完全相同。把 T=1 那一列取对数除以 1.307 再 softmax，**逐项复现**服务读数，最大偏差 **7.77e-16**、`choice` 字段翻转 **0 次**——「零训练 ⇒ 温度只动数值」在这里不是文档里的说法，而是能在产物上验证的。代价要说清楚两点：那个 run 的 `response.model` 写着**旧名 `rlcd-qwen3.6-35b-a3b-letters`**、`/health` 里还没有 `profile` 段，**它不是当前 HEAD 的产物**；而且 1.307 是 Qwen 基座的**旧**温度，当前值是 1.506（其 §14.1、§15.1）。这是第七种表现：**温度是随代码发布的常数，但它的效果可以在别人的 committed 读数上逐位重放**。

## 4. 同一个坑，各踩各的

这一节是并读十五条才有价值的部分：同一个失效模式在多条路线上反复出现，**修法不同、能不能被发现也不同**（也有实现显式记下「无此坑」）。

### 4.1 `enable_thinking=False`：一条坑，几种接法与六种不适用

读位置落进 `<think>` 块，概率质量到不了选项标记上——各条路线都踩过或绕开过，发现方式与修法各不相同；Laya、CLM 与 Kev 则根本没有这个位置，Semantic Router 与 Kev 连模板都不经过；decider 恰好相反——它的 chat 布局**有**模板，于是它把「思维块」显式闭合掉并加断言，而不是只关开关；Nimble 是**唯一能把这条坑量出来、却在发布路径上量不到的实现**——`marker_mass` 的直接对应物只在旧路径产得出（表末）。decisio 走的是第五条路：**不关开关，而是把「闭没闭合」写成断言**——`chat` 模式下模板若把思维块留开，`chat_wrap` **直接抛**（`letters.py:154-155`），而 Gemma 基座的答案位就是模板自己的第一个助手位置（`answer_slot="template"`，`:285`），所以「模板把思维块留在哪儿」直接决定读位置（其 §3）。H2O-Lightning 走的是第四条路：**不依赖模板开关**，而是把空的 `<think>\n\n</think>\n\n` 连同 `Answer:` 一起硬编码进 prompt 字符串（`h2o_lightning_shim.py:73-75`），并**直接拒绝** `enable_thinking` 为真的配置；模板只在图像路径上被用到，而那条路径用一条断言保证「模板渲染 == 文本渲染」（其 §3、§10）。

### 4.2 填充方向：两条都精确，依赖的性质不同（外加一层「候选位」填充）

| 实现 | 填充方向 | 为什么不影响结果 |
|---|---|---|
| RYOTIDE | **右填充且不传 mask**（torch 批量读） | 因果模型看不到自己之后的 padding |
| Open-Jev | **右填充**（`padding_side = "right"`） | 同上，不污染真实末位置 |
| Quyet | **左填充且必须传 mask** | 位置整体平移，RoPE 只看相对距离；padding 由 mask 屏蔽 |
| Laya | **右填充且必须传 mask**（`pad_batch`，`backends/base.py:41-71`） | 它是**双向**编码器，padding 在左侧也会被 attend 到，所以 `right` 并不自动安全，必须靠 mask；另外填充行**特意留一个活 marker**（`:59-68`），否则全掩码行变 NaN——而批里一个 NaN 就足以毒掉 CUDA graph 的 replay |
| SemIf-OpenJev | **两条方向在同一个仓库里并存**：`shared` **右填充** + 显式 `position_ids`（padding 位给 0），读**记录下来的每条末位**（`shared.py:47-50`）；reranker **左填充**，读 `[:, -1, :]`（`reranker.py:64-67,77`） | 右填充那条靠因果性 + 位置显式给定（`attention_mask` 也传了）；左填充那条靠 mask。真正的坑不在方向，在**「末位」这个词**：批内有 padding 时，`shared` 模式必须读每条自己的末位，读 `-1` 会读到 padding（其 §7.3） |
| OpenJev(HF) | **不适用**：这份代码**不组批**——它按题并发请求（`shim.py:320` 的 `ThreadPoolExecutor.map`），每个请求一个 prompt，填充由 vLLM 内部处理 | 补丁里唯一与「对齐」有关的东西是 `SHIM_PAD`（`shim.py:92-102`）：往共享前缀里塞 `" pad"` 填充，把 header+prefix 顶到 784 的块边界，为的是**缓存块命中**而不是批内对位。它甚至为此对 BPE 合并做了三次迭代修正，且**发布配置里是关的**（其 §8.2） |
| decider | **右填充，两条库路径都不传 attention mask**：`Engine` / `EngineV2` 的 `_fwd_eager` 只传 `input_ids`（`engine_v2.py:114-116`），`fill_ids` 用 pad token 右填充到桶长、短行补在后面（`engine.py:59-63`） | 因果层 + 右填充 ⇒ pad 位置不影响更早的槽位，所以掩码可以省——这正是「每种 (B, 桶长) 形状捕获一张图反复重放」的前提（`engine.py:1-6`）。**唯一必须传 mask 的前向是 schema 缓存**：后缀行拼在一条**只读前缀**之后，掩码要同时表达「本行只看得见自己那条前缀（而不是补到 `tpmax` 的 padding）」与因果性（`schema_engine.py:84-89`）。GGUF 路径另有一个不透明后端的行为：`n_seq_max > 1` 把多行打包进一次 decode 会**移动概率**（源码记 BF16 最多 0.02、Q4_K_M 最多 0.16），所以默认 1、且每次 decode 前清空 memory（`engine_gguf.py:9-12`、`:98`） |

| vLLM Semantic Router | **两条 runtime 都是右填充 + 必须传 mask**：encoder 填到批内最长（不对齐倍数，`vela.py:171-189`），decoder 填到 **32 的倍数**（`segments.py:78-95`）；两边都把 `attention_mask` 一路传进 attention 与题型头的 `key_padding` | encoder 是**双向**编码器，右填充**并不自动安全**，必须靠 mask（与 Laya 同一处境）；decoder 是因果的，本可省，但代码照样传。**这个仓多一层别的实现没有的填充**：候选位填充——选项数少于批内最宽行时补 0，并用 `candidate_mask` 打到 `-inf`（`segments.py:82-95`、`candidate.py:77-82`）。所以「填充」在这里有**两级**：token 级与候选级，屏蔽手段不同（前者靠 mask，后者靠掩码 logits） |
| CLM | **不适用**：这份代码**不组批**。`Embedder.embed` 把待编码的文本按 32 条一批发出去（`embedder.py:31,71-79`），批与填充**全在 vLLM 内部**；本仓拿到的是一个已经归约好的 `[n, 4096]` 数组，再一次性喂给 head（`heads.py:104-109`） | 仓里从头到尾没有 `padding_side` / `attention_mask` / pad token 这些东西（grep 零命中），因为**没有一个张量是本仓拼起来的**。于是「填充方向」在这里不是「选得对不对」，而是**没有这个决策**——这与它的读位置处境恰好相反：读位置它也是推给别人的，但那个决策会决定答案，而填充不会 |
| Kev | **右填充 + 必须传 mask**（`_pad_rows`，`model.py:303-314`）：把一批行补齐成 `[N, L]`，填充位给 `pad_id` 并在 attention mask 里置 0；在 MPS 上 eval 模式的 `L` 还会**向上取整到 64 的倍数**（`SHAPE_BUCKET`），纯粹为了按形状预热 kernel | 填充位永远排在真实 token 之后、且被标成非参与键，所以真实 token 的隐状态不受影响（注释：*parity measured exact*）。真正的关键在于**读出用的是 `rows_of` 记下的行内相对下标**（`model.py:188-202`：`decide` 与 `opts`，以及 `opt_idx`），**不是 `-1`**——所以批内填充再多也读不到 pad。这与 SemIf-OpenJev 的 `shared` 模式是同一个纪律，只是它靠「显式记录位置」，Kev 靠「位置本来就是算出来的」 |
| Nimble | **右填充，且只填在自己 fork 出来的分支上**（`parallel_scorer.py:136-137`）；CUDA 路径**不组批**（每题一条序列，`cuda_scorer.py:141-142`） | 分支的 padding 排在真实后缀 token 之后，因果性保证它不影响读出的那个位置；而读的是**每行自己的末位** `lengths-1` 而不是 `-1`（`:142`）——这一步不是风格选择：共享前缀下各 field 的后缀长度天然不等（committed 记录是 `[13, 13, 14]`），读批的 `-1` 就会读到 padding。与 SemIf-OpenJev 的 `shared`、与 Kev 的显式下标是同一条纪律；另外分支 cache **用完即弃**、源前缀从不被分支更新（`:139-140`、`:151`） |
| Jevlike | **右填充，两处 mask 都必须传**（`data.py:87-107` 造掩码，`model.py:38-43` 用掩码） | **这个头对 state 不是因果的**（没有 causal mask），所以右填充**不自动安全**，必须靠 `context_mask` 打到 `finfo.min`——与 Laya、Semantic Router 的 encoder 同一处境。另有一层与它们同类的**候选位填充**：批内某行选项数少于最宽行时补 pad，由 `option_mask` 掩掉（`:43`），于是外层 softmax 把不存在的槽位恰好压成 0 概率。字节路径的 pad 分离得很干净（pad id 是 0，真实字节都 `+1`，`data.py:50`）；hf 路径的 `pad_token = eos_token` 回退则有一处副作用（其 §2.4） |
| H2O-Lightning | **不适用**：这份代码**不组批**——一次请求里的每个问题各自发一次 completion（`ThreadPoolExecutor`，`h2o_lightning_shim.py:912`、`:996-998`），批与填充**全在 vLLM 内部**；`serve_config.json` 与 shim 里都没有 `padding_side` / pad token 这类设置 | 「填充方向」在这条链上不是「选得对不对」，而是**没有这个决策**——与 CLM 同一处境。真正要对齐的是另一个量：**共享前缀的长度**。多问题时它用 `common_prefix_len`（`:891-899`）算出共享头并**只计一次**（`:1059-1060`），图像路径还要把 vLLM 展开的图像 token 差额补进共享头（`:1047-1049`）。错的是账、不是答案：`test_shim.py:214-233` 断言「一起问」与「逐个问」的答案逐字节相同（其 §7） |
| decisio | **前填充（`front`）是服务默认，另有 `between` / `user` 两个可选位置**：`pad_prompt`（`vllm_engine.py:118-131`）在三个位置之一插入 k 个填充 token，`k = (-n) % pad_unit` 让 **state 的边界**落在块边界上（`--pad-policy row` 则让**整行**落在边界上，`:508-512`） | 填充不是为了让批内对位，而是为了让**前缀缓存的命中单元**落在 state 的边界上：vLLM 在这台混合架构上只在块边界存 Gated DeltaNet 的状态，切在块中间的共享前缀会被每道题重新预填充（`vllm_engine.py:13-17`）。**位置是被测量过的自由度**：`between` 是第一个做法，注释记它 *moved 9.4% of top answers against the unpadded prompt*（`:123-124`）；committed 的 `runs/2026-10-02_pad-policy-row/conformance_l1.json.gz` 是 C4 门**唯一一条 FAIL**，max \|Δp\| = 0.0147 而翻转 0（其 §8.2、§14.4）。另一端 `none` 是 MLX 的默认：MLX 的缓存不需要填充，去掉它才使「一道题单独问」与「在一组题里问」是同一个 prompt（`:1016-1019`） |

Quyet §6 给了实测（随机初始化 2 层 Qwen2）：位置整体 +36 → 差 **0.0**；左填充 + mask → **5.96e-08**；左填充**漏传 mask** → **0.166**。所以「一边能省掉 mask、另一边不能」不是风格差异，是被依赖的性质不同。

### 4.3 线性注意力 / 混合架构的 cache 坑

| 实现 | 坑 | 结论 |
|---|---|---|
| RYOTIDE | `ArraysCache`（线性注意力层，固定大小 recurrent state、无 offset 可回卷） | 只复制**列表**即可——槽位是写时重绑而非就地修改 |
| RYOTIDE | `RotatingKVCache`（Gemma 4 的滑动窗口层） | 必须**给每个分支自己的 buffer**：环形缓冲绕回后 `state` 交回的就是 buffer 本身，就地写会**写花父级** |
| RYOTIDE | `trim_to()` 遇不可回卷的层 | **直接报错**，而不是静默 no-op——否则一个问题会泄漏进下一个 |
| Open-Jev | transformers 5.10.2 里 `LinearAttentionLayer` 未实现 `batch_repeat_interleave` | `fork_cache` 手写；浅拷贝或只拷 KV 会让递推状态**别名**，污染后续候选 |
| Open-Jev | 库用 **conv dtype（bf16）** 分配递推状态，而 delta-rule 状态本应是 FP32 | `RecurrentDtypeLayer` 精度补丁，强制保留 kernel 输出的 dtype |
| Jeff / Quyet | 无此坑 | 每问题独立完整前向、无 KV 分支，用简单性换掉了这一整块复杂度 |
| Laya | 无此坑 | **编码器根本没有 KV cache**，也没有递推状态。代价不在内存而在计算：双向编码器**无法复用前缀**——每个 token 的表示都依赖整段 state，换个 state 就得整段重算（其 §7） |
| SemIf-OpenJev | 分支复制写成 `cache.reorder_cache(torch.zeros(len(rows)))`（`shared.py:128`）——语义就是「把第 0 行复制 N 份」 | 对纯注意力 cache 够用；换成带递推状态的 cache，复制的就是状态本身。所以有**两道守卫**：`cache.get_seq_length() != len(prefix)` 与 `reorder_cache` 不可调用时**直接报错**（`shared.py:95-98`，原话 *Native cache does not support duplicate branch selection*）。MLX 侧改用 `entry.merge([entry]*N)` + `entry.prepare(lengths, right_padding)` 显式告知每条分支的真实长度（`mlx_backend.py:215-217`）；llama.cpp 的 cache 不透明，只能整段 `save_state` / `restore_state`（`llamacpp_backend.py:380-391`） |
| SemIf-OpenJev | **加速本身是有损的**：`serial` / `parallel` 相对 fresh 有 5/777 与 6/777 的 argmax 翻转、最大概率差 0.0934 / 0.0624 | 源码把容差设成**故意不设门槛**（*Tolerance is deliberately non-gating*），README 也照写「BF16 execution changed 5–6 of 777 argmaxes」。这是明说「快 8.6 倍，代价是 6 个决定变了」的地方（其 §7.5）；vLLM Semantic Router 的 `shared_context` 是同一类交易，也把漂移写进了记录（其 §7.3） |

### 4.4 置信度：读出来的 vs 训出来的

这是十五条路线最根本的一条分界，也决定了「温度能不能事后单独拟合」：

- **RYOTIDE 读**：分布是模型自己的 softmax，训练不参与。于是温度**不可能改准确率**，可以被离线拟合、被预先注册的判据接受或拒绝（§2）。
- **SemIf-OpenJev 也读**，而十五条里**连「训练本身」这一环都不存在的只有三条**：RYOTIDE、SemIf-OpenJev 与 decisio。
  SemIf-OpenJev 的链条上只剩温度一环。代价是它的**拟合比 RYOTIDE 更宽松**：三个 T 无条件发布，没有接受 / 拒绝判据；换来的是它把折外 ECE、group bootstrap 区间和池化负对照一并提交（其 §12）。它也因此能实测出「T=1.2342 在 144 行上翻转 0 个 argmax、平均 top-1 从 0.8628 降到 0.8333」这种干净的单调性证据。
- **decisio 也读**，而且是这三条零训练路线里**唯一把「温度只动数值」做成可逐位复算的一条**：
  `runs/2026-09-30_served-default/decision_index/` 下一对 run（`temperature_1` 与 `default`，各 20,810 行、
  `run_id` 集合相同），把 T=1 那一列取对数除以 **1.307** 再 softmax，逐项复现服务读数，最大偏差
  **7.77e-16**、`choice` 翻转 **0 次**（其 §14.1）。它比 RYOTIDE / SemIf-OpenJev 多一层的是**服务面**：
  同一个引擎的读数在 `/v1/answer` 上是未加温度的原生分布、在 `/v1/systemone` 上是加过温度的，
  而 C4 门在比较两条路由前**显式把温度补回去**（`systemone_conformance.py:318-335`，判据是
  `max_abs_delta_p == 0.0` 且翻转 0）。它的温度也不是一条曲线而是**两张表**：全局一个、choice 一个，
  逐基座覆盖（Qwen 1.506 / 1.370，Gemma 12B 3.592，Gemma 31B 5.252 / 4.672）——**三个基座的 T 都远大于 1**，
  与 H2O-Lightning 的 0.65–0.8 方向相反（其 §10.2、§2）。
  **它另有三处可选、逐任务的拟合（先验 bias / intent head / 拒答阈值），但没有一处改的是权重**，
  而且每一处都带一条写死的接受判据，不通过就存「关」并写明理由（其 §10.3）——所以严格说它是
  「读出来的 + 三个默认关闭的可选修正」，而不是「训出来的」。
- **Jeff / Open-Jev / Quyet / Laya / OpenJev(HF) / vLLM Semantic Router / CLM / Kev / decider / Nimble / Jevlike 训**：训练本身就在改数值、也可能改 argmax。温度退化成**训练之后的二次校正**，不再是唯一变量。
  - 这一组里 **Nimble 是唯一把「拟合判据」做得与 RYOTIDE 同级严格的**：温度只在 300 条训练外样本上按 log loss 拟合，然后**先在另一批 300 条上注册判据再验收**（log loss 必须降、Brier 不得升，`README:509-511`），并通过。代价是它**同时留下了反向证据**：同一个温度在 holdout 上把 ECE 从 0.052 抬到 0.054、在 64 道 rating 题上从 0.105 抬到 0.177（其 §9.2）。所以「温度只改数值」在它身上既不是无条件发布（Open-Jev / Laya 那种），也不是恰好成立——是**测过、有得有失、按预先写下的规则接受了**。
  - Nimble 另有一处与这一组其余实现方向相反：它**只有一个 checkpoint 拟合过温度**，其余（包括最新 checkpoint 与 v2）要么默认 1.0、要么继承那个数，而且**身份按哈希判定**——revision 传短哈希会静默落到 1.0（其 §9.2）。
  - Kev 是这一组里**把「训练看不到温度」写得最干净的一条**：`PointerHead.forward` 只在 `not self.training` 时才除温度（`model.py:218`），而 `kev/train.py` 全文没有 `temperature` 这个词。所以「温度只动置信度」在这里不是恰好成立，而是**由构造保证**——但它也因此**测得到自己的边界**：T 不改同一题内的 argmax，却会改**跨题**的置信度排序（`AGENTS.md:445` 原话：*Temperature can reorder confidence across multiclass questions, even at fixed option count*），而单温度**无法**让 A 题更自信、B 题更不自信（`README.md:431`）。它的拟合还比别家多一道门：脚本会**拒绝**在训练语料的留出条目上拟合的行（`scripts/calibrate_checkpoint.py:1-28` 记了 round 19 的失败模式：ECE 0.059 → 0.0085），**四个发布温度全都过了这道门**（其 §9.3）。
  - decider 是这一组里**把「置信度」分成三层写清楚**的一条：①训练改数值（§2）、②温度只改数值（这一点在 committed pins 上验证过——四个温度下 argmax **翻转 0 次**，其 §14.1）、③而**报出去的 `confidence` 又由一套公式决定**——`system_one()` 用 TypeSafe 的 rescale，`decide()` 用 `p_max`。所以「这个 `confidence` 是哪个数」在**同一个包里**就得先问清是**哪条 API**。它另有一处只有它才有的口径：温度**分 state-first 与 schema 缓存两套**（`temperature.py:109-112`），而 schema 缓存是**掉准确率**换速度的可选档（`infer.py:139-141` 的注释记约 1.5 个百分点），于是同一个进程的两条路径会给出两个数，而 `/health` 会把两套都回声出来（`serve.py:554-559`）。
  - 与之相对，decider 的**拟合环节比别家薄**：`calibrate.py` 按 NLL 在 0.05–20 的 801 点网格上拟 by-type 温度（`calibrate.py:27`、`:145-179`），但它**只 print JSON**，写回 config 是人工步骤（`scripts/evaluate.sh:13` 的注释），而且**没有接受 / 拒绝判据**——这一点与 Open-Jev、Laya 同宽松，与 RYOTIDE 的预注册判据、Kev 的留出集闸门都不同。
  - Jevlike 是这一组里**把「没有二次校正」推到尽头的一条**：它训的是**全部参数**（tiny）或**一个头**（hf），
    而链条上**只有训练这一环**——没有拟合出来的 T、没有 ECE 门槛、没有接受 / 拒绝判据、没有随权重发布的常数，
    **也没有每请求的入参**。`eval.py:37-43` 确实算 ECE，但只 print、不改任何数（10 个等宽箱，§5 第 2 条）。
    所以第 4 条不变量在它身上要改写成「无可确认」，而不是「先去确认 T」（其 §9.1）。
    一处必须分清：全仓唯一的 `temperature` 是**下棋时采样按键的旋钮**（`examples/chess/eval.py:72-73`），
    它改的是游玩时选哪个键，不改任何报出去的置信度（其 §9.3）。
  - CLM 是这一组里**唯一没有「二次校正」这一步**的：它训了两个投影（`finetune.py:174-183`），
    但**没有任何标定产物**——没有拟合出来的 T、没有 ECE、没有接受 / 拒绝判据、也没有随权重发布的常数。
    它连「训练之后施加的常数」这个环节都不存在，只剩一个**每请求的入参** `temperature`（`engine.py:105`），
    默认 1.0、不回声（其 §10.2）。所以「这个概率是在哪个 T 下产生的」在 CLM 上不是「要去包里查」，
    而是**要去问调用方**——它自己那批 committed 记录是靠「请求体里没有这个键」才定下 T=1.0 的（其 §14.1）。
  - vLLM Semantic Router 是这一组里**唯一把「逐 runtime 不同」摆到台面上**的一条：同属一个 `decision1` 家族，
    encoder 三条**完全没有温度**（包带 `calibration` 就拒载），decoder 四条**必有一个温度**（其 §5.3、§10.3）。
    它的标定链还比别家多两样：Decision 2.0 的 `score_bias`（按等级数查表的 logit 偏移，**绑 `model_sha256`**）
    与 Vela 2.0 的阈值族（PII 长度规则、稀疏文档闸门，其 §10.2）。
  - OpenJev(HF) 是这一组里**把「训练改了 argmax」量化得最直接**的一条：同一批选项打乱顺序，微调前翻转 18.5%、微调后 2.3%（`README.md:109`）——温度不可能做出这种改变，它是训练做的（其 §7）。代价随之而来：它发布的三个常数**与代码默认值全不相同**，且是在另一个读数协议下拟合的（§2）。
  - Open-Jev 对此最宽松：拟合值**无条件写入**，没有接受 / 拒绝门槛（其 §6 注：*"Calibration temperature is not a held-out capability or safety result"*）。
  - Laya 同样**无条件发布**（`train.py:1138`），且发布路径上的 `clamp` 自己承认 *The clamp bounds the damage; it does not calibrate anything*（其 §10.3）。
  - Quyet 把它固化进权重包：T 与「缺键 = 1.0 = 未校准」的默认一起发布。
  - H2O-Lightning 是这一组里**唯一没有「拟合」这一步、却仍然改了发布数值**的一条：它的逐题型温度（`choice 0.75 / noul 0.8 / score 0.65`，`serve_config.json:5`）既不是拟合产物、也不是训练后的二次校正——仓里没有拟合脚本、没有接受 / 拒绝判据、也没有标定记录，它只是**随服务发布的一份配置**。所以「这个数是在哪个 T 下产生的」在这里要问的是**部署**：两个旋钮都能被环境变量整体替换（`SHIM_TEMPERATURE` / `SHIM_NOUL_FLOOR=0`），而 `/health` 会回报生效的是哪一个来源（`:1077-1078`）。它的伙伴 yes/no 地板 0.801 则是**第六种表现**：不改 argmax（1,367 行复算翻转 0 次），但把 t=0.8 那一档的升级率从 41.0 % 抹成 **0.0 %**——不是把数值算偏，而是**把一个下游信号整个抹平**（其 §9、§16）。
- **Laya 另有一层别家没有的麻烦**：同一条答案里**两个字段都叫 `confidence`**，只有一个（`answer_confidence`）是温度拟合与 ECE 的对象，另一个是归一化熵；服务侧还会注入第三个 `x_jev_confidence`。所以 §3 的 #4 在 Laya 上要改写成「确认用哪一个」，而不只是「确认 T」。
- **vLLM Semantic Router 把这条分界又推进了一步：同仓三代，`confidence` 是三个不同的公式**。
  Decision 1.0 与 Vela 2.0 用 top-two margin（choice）/ `1 − var/uniform`（score），
  Decision 2.0 用归一化熵 `1 − H/log k`——**同一个字段名、同一个契约、同一份 golden 文件**。
  这一条在 committed 产物上可以直接验证：Decision 2.0 的记录值与熵公式**逐位吻合**，
  而与离散度公式最多差 **0.2818**（其 §10.1、§14）。再加上它的生产者与消费者各有一套：
  **Go 侧不用模型报的 `confidence`**，而是自己从 `probabilities` 重算（Choice 取选中项的概率、
  Score 取最大概率、Noul 取 P(true)），模型那个字段只被解码与范围校验（其 §10.4）。

### 4.5 「算得出来 ≠ 接进来了」

十五篇各自记了一处「代码写了却不在生效路径上」「接了却没有收益」或「生产者和消费者各算一套」，性质各不相同：

| 实现 | 位置 | 性质 |
|---|---|---|
| RYOTIDE | `calibration_bias()`（其 §9.3） | **全仓零调用点**，且六臂实验实测**没赢**（letters 0.675 vs letters+cc 0.600）——是「试过之后的结果」，不是忘了接线 |
| Jeff | `typed-*` 两种头（其 §3） | 发布路径上**不可达**：`Decider.decide` 调 `option_logits(h, k)` 时从不传 `q`，而 typed 头要求显式传入 |
| Quyet | encoder 的 `MASKED_LOGIT`（其 §3.1） | 在主路径上是**冗余**：`runtime` 只取 `lg[j, :len(markers)]`，补齐槽位本来就进不了 softmax——写了但改变不了任何数值 |
| Laya | `loss="soft-ce"` 路径（其 §11） | **加了没收益**：源码记 *#741 measured no gain from the extra term on the typed-decisions split*——策略梯度项在那份 split 上没测出收益，被诚实地记成负结果 |
| Open-Jev | 反面教材（其 §8） | `device_map="auto"` 让 12 个模块落到 disk、决策头留在 `meta`，**而服务仍然对 `/health` 回 "ready"，并从没加载的模型返回自信的数字** |
| SemIf-OpenJev | 诊断量 `allowed_token_mass` / `full_vocab_argmax_id`（其 §3） | **不在默认生效路径上**：只有 `serial.py:120-123` 与 `llamacpp_backend.py:285-286` 产出，`direct` / `shared` / `mlx` 都不产出；而 README 的 Quick start 走的正是 `--mode direct`。它是「量算得出来、也确实有用，但最常用的那条读法不上报它」——与 Laya 那条（接了没收益）方向相反，是**有收益但没接到默认路径** |

| OpenJev(HF) | 读数协议 `READOUT_TARGETED` 与三个常数（其 §13.2） | **默认路径与发布路径不是同一套**：文件默认 `TARGETED` 关、T=1.1、noul=(3.0,−0.4)；发布配方是 `TARGETED=1`、T=0.85、noul=(1.829074, 0)，而 T 与 noul 斜率**正是在 TARGETED 打开时拟合的**。`python helper/shim.py` 直接跑起来能得到格式完全正确、数字看似合理的回答，用的却是为另一套读数拟合的常数 |
| vLLM Semantic Router | 模型答案里的 `confidence` 字段（其 §10.4） | **算出来了、契约要求有、也被校验了，但决定路由的不是它**。Python 侧按 `decision_type_aware_v1` 算出 margin / `1−var`，写进每一条回答；Go 侧把它解码进 `Answer.Confidence`（`client.go:408-409`）、要求它落在 [0,1]（`answer_check.go:35`），然后**另算一套**用于信号门控与排序：Choice 取**选中项的概率**、Score 取**最大概率**、Noul 取 P(true)（`classifier_signal_decision_model.go:167-200`）。所以同一个名字下有**两个数**，而拿哪一个是调用方看不见的。这与上面 OpenJev(HF) 那条方向相反：那条是「接了但要配对才生效」，这条是**「两条链各自都自洽，只是不是同一条」** |

| CLM | `label_of` / `probabilities_of`（其 §10.3） | **定义了、没有调用点、也没有进包的门面**：全仓 `grep` 只有 `schema.py:152` 与 `schema.py:163` 两处定义，`src/clm/__init__.py` 里既没有 import 也没有列进 `__all__`（对比同一模块的 `build_pairs` / `candidates` / `state_text` 都在 `__init__.py:17` 被导出）。它真正值得记的是**它和响应字段是两个不同的归约**：`label_of` 对 `score` 取 **argmax 档位**，而答案里的 `score` 是**期望档位**（`Σ i·p_i`）——下游拿哪个算准确率会得到不同的数，而本仓不给示范 |
| Kev | 四条「写了但没发布」的路径（其 §14.2） | **四种性质各不同，且 Kev 全部记在明处**：①`option_isolation`（构造性置换不变，`model.py:116-118`）**默认关**，且混合骨干**不支持**（`model.py:263`）——当前全家族都是混合骨干，所以这条路径在发布版上**不可达**；②`--perm_kl` 对称 KL 项**默认 0.0**（`train.py:381`，`--perm_frac` 默认 0.3）；③`RotationAveraged` 测试期顺序平均要 `rotations >= 2` 才生效，而 committed 的 report 里 `rotations` **全是 1**；④三个可选损失 `--label_smoothing` / `--brier_w` / `--focal_gamma` 是**一次注册过的筛选筛完没有候选通过**（`AGENTS.md:446` 原话 *exist but ship in nothing*）——**不是忘了接线，而是接过、测过、记录了负结果** |
| decider | 两条「写了但不在默认路径上」（其 §6、§9.3） | **①反转重读平均默认关**：`second_reading` 的实现完整（`serve_vllm.py:139-159`）、连测试都在（`tests/test_serve_vllm_second.py`），但它要 `decider_config.json` 显式给出 `below` 与 `temperature_by_options` 的 a、b 才生效，默认是 `SECOND = None`（一次读数，`serve_vllm.py:84`）。**②真正存在的那个诊断量没人看**：`marker_mass` 在这里没有对象（词表维度不出现，§3 表 #1），而实际被计数的是「未知 cache 布局导致的降级」`shared_unchunked_layout`——它只出现在 `/stats` 的 `engine` 字典里，**没有任何告警或响应字段带着它**（`shared_prefix.py:207-210`、`serve.py:562-566`）。这与 SemIf-OpenJev 那条同类（有效但没接到默认路径），比 Laya 那条（接了没收益）更轻也更隐蔽 |
| Nimble | ①整套 `QwenEnumScorer` + `binary_logits` 读数（其 §5、§9.4）；②顺序偏置的度量工具（其 §6） | ①**写完了、有测试、有 committed 样例，但不在任何发布数字的路径上**：那是仓库里最早的那套 MiniCheck 式读数（1-token 解码 + 词表掩码 + `marker_mass` 对应物），`tests/test_enum_scorer.py` 逐项测它、`examples/priority_results.json` 是它的输出，而 324 holdout 的准确率与 13 个公开子集全走 `evaluate_public.py → build_scorer → ParallelScorer/CudaCandidateScorer`。**代价是诊断量被一起留在旧路径上**：唯一能量出 `marker_mass` 的地方，恰是发布链不走的那条（其 §10 表 #1）。②**工具在、实验不在**：`--shuffle-seed` 与 `selected_code_counts` 都实现好了（`evaluate_public.py:102-105,139-147`），上游文档却写着 *No shuffled run has been made yet*（其 §6）——不是「写了没生效」，是**写了、备好了、一次也没跑** |
| Jevlike | 三条「写了但不在生效路径上」（其 §13） | **三种成因各不同**：①`PlainConvPolicy` 这个架构对照臂**不可达**——`audit.py:72` 只在 `payload.get("model_type") == "plain_conv"` 时用它，而**全仓没有任何一处写 `model_type`**，所以本仓产不出能进这个分支的检查点；②`examples/chess/stem.py` 的 `widen()` **零调用点**，且它的 docstring 声称「checkpoints record it as `payload["stem"] = "wide"`」——**全仓没有一处写或读 `payload["stem"]`**，是描述与代码脱节；③`config["width"]` 在 hf 分支**从不被读**（`make_system:115-125` 只用 `hf_model` / `rank` / 两处 token 预算），`--width` 照样可传、照样写进检查点，但改变不了任何行为 |

前三条是「写了没生效」，Laya 那条是「接了没收益」，SemIf-OpenJev 那条是「有效但有条件」，OpenJev(HF) 那条是「接了但要配对才生效」，Open-Jev 那条是「生效了但是没有效」，CLM 那条是**「两个归约都在，但没人用其中一个」**（比前几条更轻：不是接线断了，而是压根没有消费者），Kev 那条是**「接了、测了、然后诚实地记成负结果」**——四种状态都写在代码与文档里，而不是靠读者从缺口反推，decider 那两条则是**「代码在、测试在，但默认关」加「量在、没人看」**（比「写了没生效」轻，因为前者一改配置就生效、后者只是没有消费方），vLLM Semantic Router 那条是**「生产者与消费者各算一套，两边都不报错」**——最后两条最难发现，因为它们连错都不报。Jevlike 那三条又各是一类：①**读者在、写者从没有过**——`PlainConvPolicy` 这个架构对照臂在 `audit.py:72` 被读，
而全仓没有任何地方写 `model_type`，所以本仓产不出能进那个分支的检查点；②**描述与代码脱节**——`examples/chess/stem.py` 的 docstring 声称
*checkpoints record it as `payload["stem"] = "wide"`*，而全仓没有一处写或读 `payload["stem"]`；
③**同一份 config 服务两条分支、只有一条读它**——`config["width"]` 在 hf 分支从不被读（`make_system:115-125`）。
三者都不报错、也不改变任何数值：前两条会让「试过的实验」看起来可复现，第三条会让「我刚调了 width」这个判断失效（其 §13）。
Nimble 那两条各是新的一类：①是**「整条旧读数连同它的诊断量一起被留在发布链外」**——不是接错线，是**换了一条链之后旧链的产物没人再引用**，而它恰好是唯一能产出 `marker_mass` 的地方，所以这不是「轻」而是**能力上的净损失**；②是**「工具写好了、一次对照也没跑」**——比 Kev 那条更轻也更诚实：Kev 至少跑过了并记下负结果，Nimble 连跑都没跑，并且把这一点写进了文档而不是留给读者从缺口反推。 H2O-Lightning 那条是**第六种**：**「接了、校验了、然后自己说没实现」**——`effort` 档位被接受、被校验、也在响应里回声（`h2o_lightning_shim.py:976-981`、`:1061-1065`），但它**从来没有被实现过**，而代码把这件事写进了每一条带非 `fast` 档位的响应里。它比「写了没生效」更轻（数值完全不受影响），比 Kev 的「测过、记负结果」更早一步——**它连测试都还没有，先把话说在响应里**（其 §8）。
decisio 那条是**第七种**：**作者写全了、注释也写了，而读者从来没有过**——`consonant_pair_pool` / `order_pool` /
`pool_prior_prompt` / `LABEL_SCHEMES` 四个函数/常量只有定义，`letters_prompt` 的 `pool` 形参从未被传过，
而服务路径走的是**没有 `pool` 形参的** `question_body`（`letters.py:248-263`）；更麻烦的是注释指着
`--labels consonant-pairs` 这个**本仓不存在的 flag**（`letters.py:33`）。它与 Jevlike 的 `PlainConvPolicy`
（读者在、写者从没有过）恰好相反，比 Nimble 那条更轻（Nimble 是整条链被换掉、能力净损失），
但比 Laya 那条更难发现——**因为注释本身在替它作证**（其 §6.2、§15.3）。

## 5. 数字的可比较性：十五处口径不一致

跨实现引用概率、准确率、ECE 之前，有十五组口径必须先对齐，否则会得到看似合理的错数。

1. **温度**（§2）。十五篇都记录了同一个现象：同一条记录、同一个 argmax，顶部概率可以差一个量级。
2. **ECE 分箱**。RYOTIDE 走的是 vendored JevBench 的 **10 个等宽分箱**（`vendor/jevbench/jevbench/metrics.py:55`）；Open-Jev 与 Laya 各自实现的是 **15 箱**（分别 `metrics.py:98` 的 `n_bins=15`、`common.py:766` 的 `bins: int = 15`）。**10 箱与 15 箱的数字不可直接互比**（Open-Jev §6 明确记了这一点）。SemIf-OpenJev 用的是 **10 箱**（`benchmarks/calibrate.py:134` 与 `benchmarks/evaluate.py:135` 都是 `bins=10`），Nimble 也是 **10 箱**（`evaluate_public.py:18` 的 `BINS = 10`，`evaluate_public.py:72-88`）——这两条与 RYOTIDE 在这一层同口径，与另外两条不同。Nimble 的报告里还把口径本身写进产物：`"confidence": "top candidate probability; no temperature has been fitted"`（`evaluate_public.py:157-159`），也就是**那批公开基准的 ECE 是在 T=1.0（未校准）下算的**，而它们的 revision 也不是有拟合温度的那一个（§2）。
3. **calib 轴的公式**也可能不是一个。RYOTIDE 记录了看板上它那一列的 calib 与官方列**并非同一个式子**（本地评分只用 ECE，官方在能拿到 gold 分布时还加一项 TVD，其 §9.5）。
4. **归一化常量与分桶边界**。Quyet 与 Laya 都用 `2 / 3-5 / 6-10 / 11+` 这套选项数分桶（Quyet 其 §5、Laya 其 §10.2），而 Laya 的 act 头还用 `k / 255.0` 归一化选项数（`common.py:650`）。同一个「11+ 桶」在两边指的不一定是同一组候选规模。
5. **「已校准」与「未校准」是两份文件，不是同一个数的两个版本。** SemIf-OpenJev 把温度改写过的概率写进**另一个文件**（`results/raw/calibration/*.calibrated.jsonl`），原文件不动，并且在改写过的每一行留下 `calibration: {method, temperature}`（`calibrate.py:345-346`）。引用一个概率之前，先看文件名里有没有 `.calibrated`——这与「确认 T 是多少」（第 1 条）不是同一件事：**T 是参数，文件是身份**。
6. **「代码里的默认值」与「发布配方」是两套数。** OpenJev(HF) 的三个标定常数（T 1.1 → **0.85**、noul 3.0 → **1.829074**、bias −0.4 → **0**）与两个行为开关（`READOUT_TARGETED` 默认关 → 发布 **开**、`READOUT_INSTR_STYLE` 默认 JSON → 发布 **pyrepr**）的默认值**全都不同于发布值**（其 §13.2），而 T 与 noul 斜率正是在 `TARGETED` 打开时拟合的。**照 README 抄那两行命令**与**直接 `python helper/shim.py`** 得到的是两套数，且后者不会报错。这是这一组里最典型的一条把「怎么跑」本身变成口径问题的地方（CLM 有一个**方向不同**的同类问题：它的口径不在「怎么跑」而在「**怎么传**」——同一份代码、同一条命令，只因为请求体里多一个 `temperature` 就换一套发布数值，而响应里没有任何东西记录它，其 §10.2；Kev 则有一个**邻近**的：同一个 checkpoint 的**已发布准确率走 fp32 evaluation path、服务默认走 bf16**，本文 §3 的「各自新增的」与 Kev 那篇 §3）。
7. **同名 `confidence` 是不同公式，甚至同一个仓里就有三套。** vLLM Semantic Router 的 `decision1` / `vela2` 用 top-two margin（choice）与 `1 − var/uniform`（score），`decision2` 用归一化熵 `1 − H/log k`（其 §10.1）——而 Laya 那边是**两个字段都叫 `confidence`**（§4.4）。这条与第 1 条（温度）不是同一件事：温度改的是**同一个公式的取值**，这里是**公式本身换了**。判据可以机械地做：拿分布重算一遍三条公式，看哪一条能对上记录值——本文 §14 就是这么做的（Decision 2.0 的熵公式对到 0，离散度公式差 0.2818）。
8. **「每请求的 token 数」在 CLM 上不是请求的函数，而是「请求 + 缓存状态」的函数。** `usage.input_tokens` 只计**未命中**（`engine.py:75-84`、`embedder.py:57-80`），所以同一个调用可以有两种数——上游自己把这一点写进了 quickstart 的注释：*38 … (106 tokens on a cold cache: option texts are embedded once)*（`README.md:90`）。这不是「口径不同」而是**这个量本身就不确定**：它随竞技场与进程内 LRU 的状态变。committed 的 T-Rex 记录里能直接看到它：CLM 的 tokens/决策逐 run 单调下降 **15.593 → 1.286**，而 Jev 是平的（563 / 543 / 573 / 540 / 557）（其 §7.3、§14.1）。引用这个数之前，先确认它是冷缓存还是热缓存下的。
9. **`output_tokens` 在 Kev 上是一个有自己定义的数字，不是 0。** 另外十四条的 `output_tokens`，要么是 0（Semantic Router 在响应组装处硬编码、CLM 是 `engine.py:138` 的字面量）、要么是硬编码 0 而实际采了 1 个 token（OpenJev(HF)），要么根本不走这个字段（SemIf-OpenJev 的浏览器路径是另一条通道），要么**把字段定义成「答案的个数」**（decisio，本文第 15 条）。Kev 的读法同样不生成任何 token，但 `usage.output_tokens` 被 `api.py:163-165` 定义成 `len(tok(json.dumps(answers), add_special_tokens=False).input_ids)`——**数的是序列化后答案 JSON 的 token**（`README.md:284` 明说 *counts tokens in the serialized answers, not generated tokens*）。所以「底线是 `output_tokens = 0`」这句话在十四篇里**只有 Kev 需要分两层说**：机制层面成立，字段层面不成立（其 §9.4）。Nimble 是**同一份代码里三种说法**，所以引用它的 `output_tokens` 之前要先问是哪个入口：库入口（`ParallelScorer` / `CudaCandidateScorer`）连这个字段都不存在；legacy `QwenEnumScorer` 走 `max_new_tokens=1` 的真解码（`enum_scorer.py:119`）；托管面是**每 field 一个 token 加一个丢弃的 warmup**——committed 的两次 smoke 记录里 3 个 field 的 `usage.output_tokens` 都是 **4**（其 §1.2、§13.3），而同一份代码库里 `benchmark_decision_latency.py:63-64` 为另一条服务面写的自陈是 `"autoregressive_tokens": 0`。
10. **同一个字段名 `logits`，温度的方向可以相反。** 别家的 rows 里 `logits` 一般是**原始** logits、T 单独记；Kev 的 `logits` 是**已经被温度除过**的——`predictors.py:140-141` 先 `softmax(z)` 再原样存 `z`，而 `z` 已由 `model.py:218` 除过 T，所以恢复原始 logits 的代码是**乘**（`metrics.py:241`）。判据机械、可在 committed 产物上做完：拿 `p` 与 `softmax(logits)` 比——Kev 的发布检查点上差 ≤ **1.5e-08**，说明两者同温；若按「`logits` 是原始值」去算 `softmax(logits/T)`，同一行会差 **0.68**（其 §13.3）。
11. **同一个包里两个 `confidence`，而且温度还分两套。** decider 的 `/v1/systemone` 报 TypeSafe 的 rescale（`systemone.py:155-173`），而 `decide()` / `decide_json()` 报的是 **`p_max`**（`infer.py:177`、`:333`、`:340`）——**后者那侧没有 `x_p_max` 可对照**，所以调用方从字段名上看不出自己拿到的是哪一个。判据机械、可在 committed 产物上做完：`tests/data/temperature_1_3_0_pins.json` 里 `Which team?` 的 `confidence` 是 **0.7597**，正好等于它的 `p_max`，而 TypeSafe 式（n=3）给的是 **0.6396**（其 §14.2）；同一份文件另有一处断言 `/v1/systemone` 的 `confidence == (n·x_p_max − 1)/(n − 1)`（`tests/test_serve_http.py:193`）。再加上它的温度**分 state-first 与 schema 缓存两套**（`temperature.py:109-112`），「哪条 API 的哪个数、在哪条布局上」在这里是三选一。

12. **同一个仓库里三个服务面对 `output_tokens` 给出三种答案——而它们都是同一条读法。** Nimble 的库入口（`ParallelScorer` / `CudaCandidateScorer`）**不生成任何 token**，统计里连这个字段都没有；legacy `QwenEnumScorer` 走 `max_new_tokens=1` 的真解码（`enum_scorer.py:116-122`）；托管面是每 field 一个 token 加一个丢弃的 warmup。committed 的两次托管 smoke 记录里，3 个 field 的 `usage.output_tokens` 都是 **4**，与 `docs/MODAL_SERVING.md` 的 *N + 1 output tokens for N fields* 逐字相符；而 `benchmark_decision_latency.py:63-64` 为**另一条**服务面写下的自陈是 `"forward_passes_per_request": 1, "autoregressive_tokens": 0`。**这不是三段口径不一致，是三个入口**：引用之前先问清是哪个（其 §1、§13.3）。这与第 7 条（同名 `confidence` 是不同公式）同类，区别在于这里的分歧发生在**同一个仓库内部**，而且**每一份产物都支持各自那一种说法**。

13. **「标签空间」可以是实例自己的选项列表，于是行与行之间不可比。** Jevlike 的 `label` 是**行内下标**（`data.py:30-31`），`cross_entropy` 直接落在这行的 N 个标量上——所以 `label=0` 在第 1 行指第一个选项、在第 2 行指另一个，**没有任何跨行的类别空间**。两个后果：①**逐类召回、混淆矩阵这类量在它身上不存在**（对比象棋那份数据有 `per_key_recall`，因为那 5 个键是固定的，`examples/chess/train.py:36-39`）；②它的 ECE（10 个等宽箱）是**在候选数逐行不同的混合批上**算的，而候选数强烈影响 `p_max`（2 个选项与 8 个选项的行进同一个箱子，其 §9.2）。这一条与第 4 条（归一化常量与分桶边界）相邻但不是同一件事：那条是**同一个桶名的边界不同**，这条是**根本没有固定的类别**。

14. **同一份 README 里，温度既是三个值又是一个值。** H2O-Lightning 的 README 第 104 行把发布温度概括成 *text temperature 0.8, image temperature 0.65*，而 `serve_config.json:5` 里文本温度是**三个**（`choice 0.75 / noul 0.8 / score 0.65`）——同一份 README 第 212 行在讲路由表时写对了。所以「文本温度 0.8」只对 `noul` 成立。这条与第 6 条（代码默认值 ≠ 发布配方）方向不同：那条是**代码与文档各一套**，这条是**文档内部两套**，而两套都不错、只是概括的粒度不同。判据机械：把配置里的 `temperature` 与 README 里三处温度写法并排读一遍（其 §14）。
15. **同一个字段名 `output_tokens`，定义是「题目数」而不是「生成量」——而且在同一条读法的三种模式下，这个定义与事实的关系不同。** decisio 的 `usage.output_tokens` 就是 `len(questions)`（`systemone.py:600`），`docs/api.md:77` 把它写成契约、C2 门断言 `r.usage.output_tokens == len(questions)`（`systemone_conformance.py:182`）。separate 模式下**每题确实采了一个 token**（`max_tokens=1`，只为拿回那个位置的 logprobs，采到的 token 从不被读），所以这个数**恰好等于**真实生成量；而同一份代码的 **packed 模式走池化 runner、一个 token 都不生成**，CPU 替身（`hf_letters.py:97` 只做一次前向）与 MLX 同样不生成，三者照报同一个数。所以它与第 9 条不是同一件事：**Kev 是字段的定义与名字不是一回事，decisio 是字段的定义与名字之外的直觉不是一回事**。引用之前先问「这个数是答案的个数，还是生成的 token 数」——在 decisio 上它**永远是前者**。

**另一处同名不同物（同类但不在上表）：** CLM 的 T-Rex 报告里 `shield_interventions` 在 **run 层与 summary 层是两个量**——run 层是 think 时刻的替换次数（`pilot.py:492`），summary 层是 `shield_interventions + arrival_saves + emergency_saves` 三个计数器之和（`run.py:131`）。复算：CLM 是 364 + 4519 + 0 = **4883**（summary 值），Jev 的 run 层**五次全是 0**，而 summary 的 28 全部来自后两项（其 §14.2）。这属于第 7 条那一类（同一个名字底下不是同一个量），只是它发生在同一份产物的两层之间。

- H2O-Lightning 那篇的**所有概率数字都来自 committed 的 `routing_reproducibility/`**，不是该文跑出来的：**本机没有 GPU、没有下载 9.1 GB 权重、也没有跑过 `test_shim.py` 或 `routing_thresholds.py`**。它的「实测」有四类——①**哈希清单**：`SHA256SUMS` 覆盖的 **7 个文件全过**；②**内部计数**：3,474 行 = choice 1,854 + noul 1,367 + score 253，两份题集 2,000 + 1,474，`served_temperature` 字段与 `serve_config.json:5` 逐题型一致；③**用自己的代码重算发布的阈值表**（不跑上游脚本），8 个格子与 `routing_reproducibility/README.md:62-73` **逐格相同**；④**复现上游自陈的三个量**：两次 pass 差额的逐题最大差中位数 **0.000500**、9/3,474 个 top 答案不同、地板使 t=0.8 的 noul 升级率从 41.0 % 变 **0.0 %**。三点必须说清楚：①唯一超过 1 个百分点的偏差（`score @ 0.9`：卡片 98.0 % vs 重算 99.0 %）**上游自己写明并给了原因**，本文在数据里指到了具体那一行（`top_p = 0.896`、`correct = false`）；②`model.safetensors` 的 sha256（`routing_reproducibility/README.md:31-32` 声称 `2d51561f…`）**未核**——该文件 9.1 GB；③一切需要 GPU 的读数（JevBench 205/231、ImageJevBench 8/8、图像验证集 87.4 %、两张延迟表）**一概未核**，只登记它们各自声明的硬件与温度条件。
- decisio 那篇的**所有概率数字都来自 committed 的 `runs/**`**，不是该文跑出来的：**本机没有 GPU、没有下载任何 `Qwen/Qwen3.6-*` 或 `google/gemma-4-*` 权重、没有装过 decisio、没有跑过 pytest，也没有那两份分词器**。它的「实测」有三类——①**温度律**：在一对 T=1 / T=1.307 的 run（各 20,810 行、`run_id` 集合相同）上逐题复现 `softmax(log p / 1.307)`，最大偏差 **7.77e-16**、`choice` 翻转 **0 次**；②**三条 reporting 公式**在 README 实例走查的全精度响应上偏差**全为 0.0**（`choice_confidence` / `score_confidence` / `score = Σ i·pᵢ`）；③**发布清单的 sha256**：`runs/2026-10-09_readme-pip-path/manifest.json` 的 `files` 段 8 个文件**全部相同**（清单自己不在里面，所以「覆盖到哪」要按键数、不能按目录里有几个文件）。四点必须说清楚：①那对 run 的 `response.model` 写着**旧名 `rlcd-qwen3.6-35b-a3b-letters`**、`/health` 里还没有 `profile` 段，**不是当前 HEAD 的产物**；②1.307 是 Qwen 基座的**旧**温度，当前值是 1.506；③K 逐题不同（实测集合 {3,4,5,6,7,8,9,10,77,151}），这正是「标签集是运行期算出来的」的旁证，但**「255 个标签里到底有几个能单 token 化」未核**——那需要那份分词器；④一切需要权重或 GPU 的读数（JevBench、ImajevBench、三张延迟表、`/health` 里的 `requests_per_question`）一概未核。另有一处 **committed 的负结果**值得单引：`runs/2026-10-02_pad-policy-row/conformance_l1.json.gz` 是 C4 门唯一一条 FAIL，max |Δp| = 0.0147、翻转 0——**同一个读法换一种填充位置，答案不变而概率会动**。

## 6. 怎么用这几篇

- **想理解一条路线**：直接读它那篇，十五篇都能独立读——它们各自的 §0 已经把与 RYOTIDE 的分歧讲清了。
- **想选型**：从 §1 的主对照表进，按「要不要训练」「候选数上限」「能不能换 prompt 格式」「多问题要不要共享 state」「要不要逐请求挑 checkpoint」五个问题筛；如果问的是「**能不能上线**」，直接读 vLLM Semantic Router 那篇——它是十五条里唯一把加载期自检、多档数值 profile、失败模式与评测闭环都写进代码的一条。如果问的是「**延迟与吞吐**」，读 CLM 那篇：它是唯一一条把决策拆成「可缓存的候选向量 + 现算的状态向量」的路线，代价是它的诊断量与守卫仍是十四条里最薄的一条——只有 Jevlike 的**文本侧**与它同级（那边连服务都没有），而 Jevlike 的视觉侧另有一套本族最厚的（其 §8、§9.3；对照 jevlike 篇 §11.4）。如果问的是「**候选数很多、还要能长文档**」，读 Kev 那篇：候选是跨度不是 token、状态可到 65,536 token，且它是唯一一条**按骨干能力切换三套共享 state 机制**的路线（其 §7、§8）。如果问的是「**一条读法要同时服务自己训的模型和第三方 stock 权重**」，读 decider 那篇：它是唯一一条把「自训」与「零训练读 stock 指令模型」放进同一个包的路线，代价是温度、布局与引擎都得按权重来源分别配（其 §8、§10.2）。如果问的是「**一条读法要跑在三种硬件/服务栈上、还要能证明权重与代码同版**」，读 Nimble 那篇：它是唯一一条把 **prompt 源码的 sha256 放进发布契约并在加载、合并、起服务三处各校验一次**的路线，也是唯一一条**同一份代码里三个服务面对 `output_tokens` 各说各话**的——代价是 prompt 从此不能改（其 §8、§10）。如果问的是「**不确定时该把哪些题交出去**」，读 H2O-Lightning 那篇：它是唯一一条把**升级阈值表连同 3,474 行逐题读数、两份第三方题集与一份 sha256 清单一起发布**的路线，也是唯一一条把「标签必须单 token」做成**加载期逐标签探针证明**的——代价是换分词器或换 prompt 布局会让服务直接 503 拒起（其 §12、§2）。如果问的是「**一条零训练的读法要拿去上线、还要能说清当前服务的是什么**」，读 decisio 那篇：它是唯一一条把**标签集做成运行期产物**（前 K 个单 token 字母码）、把**三个基座与两套被服务的布局**放进同一个进程、把**多问题共享 state 拆成三件可观测机件**、并且**在两条路由给不同数的地方配一道门把差异补回来**的路线——代价是布局与标签集从此与分词器绑定，换一个分词器就是换一个标签空间，而且它只以 400（断言）而不是静默降级的形式出现（其 §2、§7、§9.3）。
- **想踩坑**：读 §4。这一节的每一条在十五条路线上都真实发生过，且**修法不可互相照搬**——尤其 §4.1 的 `enable_thinking`（OpenJev(HF) 的模板在不传时**默认开 xhigh 推理**且 assistant 前缀不闭合；而 Semantic Router 与 Kev 那两条**根本不经过模板**，CLM 那条连模板都没有；decider 则是**有模板但对未闭合的思维块显式补闭合串并加断言**；Nimble 是三处都传死、**连回退分支都没有**）、§4.2 的填充方向（Laya 与 Semantic Router 的 encoder 都是双向编码器，右填充**并不**自动安全；SemIf-OpenJev 同一个仓库里两条方向并存；CLM 干脆不组批；Kev 靠「位置是算出来的」而不是「记录下来的」避开同一类问题；decider 的右填充能省 mask，但 **schema 缓存那条前向必须传 mask**；Nimble 的右填充分支**后缀长度天然不等**，所以必须读每行自己的 `lengths-1` 而不是 `-1`）和 §4.3 的 cache 分支复制（SemIf-OpenJev 与 Kev 都要**显式深拷递推状态**，Semantic Router **重跑后缀**并把前缀尾部的卷积窗接上，CLM 没有 KV cache 但有自己的显存竞技场，decider 则枚举状态名后逐个复制、并对未知布局**降级为一次复制全部行且只计数**，Nimble 对无法安全广播的 cache **直接报错**、对 Gemma 的环形 cache 则**整个换成逐题重算**）。
- **想引用数字**：先读 §5，确认温度、ECE 口径、分桶边界、**跑的是哪套默认值**、**同名 `confidence` 是哪条公式（以及是哪条 API 报的）**、**同名 `shield_interventions` 是哪一层**、**token 数是不是缓存相关的**、**`output_tokens` 是不是真的 0（以及是哪个服务面）**、**`logits` 有没有已经除过 T** 和记录来源。
- **本文不做什么**：不复制各篇的论证，不做十五路之外的推断。任何一条结论要落到具体代码，回到对应走查里按行号核对。
